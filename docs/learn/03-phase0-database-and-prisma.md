## 1. ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) 101

**ตาราง (table)** = สิ่งของชนิดหนึ่ง เช่น `users`, `entries`
**แถว (row)** = ของหนึ่งชิ้น · **คอลัมน์ (column)** = คุณสมบัติหนึ่งอย่าง มีชนิดตายตัว

```
users
┌──────────┬──────────────────┬─────────────┐
│ id       │ email            │ displayName │
├──────────┼──────────────────┼─────────────┤
│ clx8k2.. │ demo@nosion.dev  │ ผู้ใช้ตัวอย่าง │
└──────────┴──────────────────┴─────────────┘
```

### Primary key (PK)

คอลัมน์ที่ระบุแถวได้ไม่ซ้ำ ในโปรเจกต์นี้คือ `id`

### Foreign key (FK)

คอลัมน์ที่ชี้ไปยัง PK ของอีกตาราง เช่น `entries.userId` ชี้ไป `users.id`
ฐานข้อมูล **บังคับ** ว่าค่าที่ใส่ต้องมีอยู่จริง — ใส่ userId มั่ว ๆ จะ error ทันที
นี่คือสิ่งที่ NoSQL ส่วนใหญ่ไม่มีให้

### `onDelete` — จะเกิดอะไรเมื่อแถวที่ถูกอ้างถูกลบ

```prisma
user User @relation(fields: [userId], references: [id], onDelete: Cascade)
```

- `Cascade` — ลบผู้ใช้ → ลบ entry ของเขาทั้งหมดตามไปด้วย (ใช้กับสิ่งที่ "เป็นของ" เขาแท้ ๆ)
- `SetNull` — ลบโปรเจกต์ → งานยังอยู่ แต่ `projectId` กลายเป็น null (ใช้กับความสัมพันธ์หลวม ๆ)

📁 ดูใน `apps/api/prisma/schema.prisma` ว่าที่ไหนใช้อะไร แล้วถามตัวเองว่า
"ถ้าสลับกันจะเกิดอะไรขึ้น" — ลบ project แล้วงานหายหมด คือบั๊กที่ผู้ใช้ไม่ให้อภัย

### ความสัมพันธ์ 3 แบบ

| แบบ          | ตัวอย่างในโปรเจกต์       | เก็บอย่างไร            |
| ------------ | ------------------------ | ---------------------- |
| one-to-one   | `User` ↔ `UserSettings`  | FK + `@unique`         |
| one-to-many  | `User` → `Entry` หลายอัน | FK อยู่ฝั่ง "many"     |
| many-to-many | `Entry` ↔ `Tag`          | ตารางกลาง `entry_tags` |

⚠️ many-to-many **ต้องมีตารางกลางเสมอ** เพราะคอลัมน์เดียวเก็บได้ค่าเดียว
📁 `model EntryTag` คือตารางกลางนั้น มี PK เป็นคู่ `@@id([entryId, tagId])` ซึ่งกันข้อมูลซ้ำในตัว

## 2. เลือก Primary Key อย่างไร

| แบบ                         | ข้อดี                                       | ข้อเสีย                                                                                |
| --------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------- |
| `AUTO_INCREMENT` (1, 2, 3…) | เล็ก เรียงตามเวลา                           | **เดาได้** — `/users/5` แล้วลอง `/users/6` (ช่องโหว่ IDOR) และบอกใบ้ปริมาณข้อมูลธุรกิจ |
| `UUID v4`                   | เดาไม่ได้ สร้างที่ client ได้               | สุ่มล้วน → แถวใหม่กระโดดไปแทรกกลาง index ทำให้ B-tree แตกหน้าบ่อย (เขียนช้าลง)         |
| **`cuid2`**                 | เดาไม่ได้ + เรียงตามเวลาได้ + สั้นกว่า UUID | ต้องพึ่งไลบรารี                                                                        |

NOSION เลือก `cuid(2)` 📁 `@id @default(cuid(2))`

**ทำไม "เรียงตามเวลาได้" ถึงสำคัญ:** index แบบ B-tree เก็บข้อมูลเรียงกัน
ถ้า id ใหม่มากกว่าเดิมเสมอ การแทรกจะไปต่อท้ายเสมอ = ถูกและเร็ว
ถ้าสุ่มกระจาย ทุกการแทรกอาจต้องแยกหน้า (page split) กลาง index

## 3. Index — สิ่งที่ทำให้ query เร็วขึ้นพันเท่า

### ไม่มี index เกิดอะไรขึ้น

`SELECT * FROM entries WHERE "userId" = 'clx123'`
ฐานข้อมูลต้องอ่าน **ทุกแถว** แล้วเทียบทีละอัน (sequential scan)
มี 1,000 แถวไม่รู้สึก มี 5 ล้านแถวคือหายนะ

### B-tree ทำงานอย่างไร (แบบเข้าใจง่าย)

index คือโครงสร้างต้นไม้ที่เก็บค่าของคอลัมน์ไว้ **เรียงแล้ว** พร้อมตัวชี้ไปยังแถวจริง
การค้นหาจึงเป็นการแบ่งครึ่งไปเรื่อย ๆ — จาก 1 ล้านแถวเหลือ ~20 ขั้นตอน

```
                [ม]
          ／           ＼
      [ก-ฌ]            [ญ-ฮ]
     ／    ＼          ／   ＼
  [ก-ค]  [ฆ-ฌ]    [ญ-ย]  [ร-ฮ]
```

**ราคาที่จ่าย:** ทุกครั้งที่ INSERT/UPDATE ต้องอัปเดต index ด้วย
→ index เยอะเกินไป = เขียนช้า + กินดิสก์ จึงสร้างเฉพาะที่ query จริง

### Composite index — ลำดับคอลัมน์มีผลมาก

```prisma
@@index([userId, module, occurredAt])
```

เปรียบได้กับสมุดโทรศัพท์ที่เรียงตาม (นามสกุล, ชื่อ):

- ค้น "นามสกุล = สมิธ" → เร็ว
- ค้น "นามสกุล = สมิธ และ ชื่อ = จอห์น" → เร็ว
- ค้น "ชื่อ = จอห์น" อย่างเดียว → **ใช้ index นี้ไม่ได้** เพราะไม่ได้เริ่มจากคอลัมน์แรก

กฎ: เรียงจาก **คอลัมน์ที่ใช้แบบ = เสมอ** ก่อน แล้วค่อยตามด้วยคอลัมน์ที่ใช้เป็นช่วง

### Partial index — เทคนิคที่ควรอวดใน README

```sql
CREATE INDEX idx_reminders_pending ON reminders ("fireAt")
  WHERE status = 'scheduled';
```

📁 `apps/api/prisma/sql/custom_indexes.sql`

ตาราง `reminders` อาจมีข้อมูลล้านแถว แต่ที่ยัง `scheduled` จริง ๆ อาจมีแค่หลักพัน
index นี้เก็บเฉพาะแถวที่ตรงเงื่อนไข → **index เล็กกว่าเป็นพันเท่า**
คำถาม "reminder ที่ต้องยิงใน 5 นาทีข้างหน้า" จึงตอบได้ระดับต่ำกว่ามิลลิวินาที

### GIN index + pg_trgm — ค้นหาข้อความ

B-tree ช่วยเรื่อง `LIKE 'ประชุม%'` (ขึ้นต้นด้วย) ได้ แต่ช่วย `LIKE '%ประชุม%'` ไม่ได้เลย

**pg_trgm** เป็น extension ที่ตัดข้อความเป็นชุดตัวอักษร 3 ตัว (trigram)
`"ประชุม"` → `ปร, ระ, ะช, ชุ, ุม` … แล้วทำ index แบบ **GIN** (เหมาะกับค่าหนึ่งแถวแตกเป็นหลายคีย์)
ทำให้ค้นคำกลางประโยคได้เร็ว และยังทนการพิมพ์ผิดเล็กน้อย (fuzzy)

⚠️ Prisma ยังประกาศ index ชนิดนี้ใน schema ไม่ได้ครบ เราจึงเขียน SQL เองแล้วนำเข้าเป็น
migration ด้วย 📁 `scripts/create-index-migration.mjs` (`pnpm db:migrate:indexes`)

## 4. JSONB — และเหตุผลที่ตารางกลางชนะ

### ปัญหา

โมดูล Task/Expense/Workout/Habit มี field ไม่เหมือนกันเลย
แต่หน้า Today ต้องดึง "ทุกอย่างของวันนี้" ในคำขอเดียว

| ทางเลือก                | ปัญหา                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------- |
| ตารางแยกต่อโมดูล        | ทุก query รวมต้อง `UNION` 4 ตาราง และต้องแก้ทุกครั้งที่เพิ่มโมดูล = ขัดกับเป้าหมายหลัก |
| ตารางเดียวใส่ทุกคอลัมน์ | คอลัมน์ NULL เต็มไปหมด, เพิ่มโมดูล = `ALTER TABLE` ตารางที่ใหญ่ที่สุด                  |
| **ตารางกลาง + JSONB**   | ไม่มี constraint ในฝั่ง payload (ยอมรับ แล้วแก้ด้วย validation)                        |

### JSON vs JSONB ใน PostgreSQL

- `json` — เก็บข้อความดิบตามที่ส่งมา ต้อง parse ใหม่ทุกครั้งที่อ่าน
- `jsonb` — เก็บเป็นโครงสร้างที่ถูกแตกไว้แล้ว (binary) → query และทำ index ได้ **ใช้ตัวนี้**

```sql
SELECT * FROM entries WHERE payload->>'category' = 'food';
```

`->>` ดึงค่าออกมาเป็น text (ส่วน `->` ให้ผลเป็น json)

### วินัยที่ทำให้ JSONB ไม่กลายเป็นถังขยะ

เราบังคับรูปแบบด้วย **Zod schema ต่อโมดูล** ที่เป็น field บังคับใน interface:

```ts
readonly payloadSchema: ZodType<TPayload>;   // โมดูลไหนไม่มี → compile ไม่ผ่าน
```

📁 `packages/core/src/module.interface.ts` และการบังคับใช้จริงที่
📁 `apps/api/src/entries/entries.service.ts` → `validatePayload()`

🎤 **คำถามสัมภาษณ์:** "ใช้ JSONB ไม่กลัวข้อมูลเละเหรอ" →
"กลัว จึงย้าย schema ขึ้นไปบังคับที่ application layer ด้วย Zod และทดสอบด้วย integration test
ข้อแลกเปลี่ยนคือเราเสีย FK constraint ในฝั่ง payload ไป ซึ่งยอมรับได้เพราะ payload
ไม่มีการอ้างถึงตารางอื่น"

## 5. หลักการออกแบบที่ใช้ทั้ง schema

### Soft delete

ไม่ลบจริง แต่ใส่เวลาลงคอลัมน์ `deletedAt`

```ts
// ลบ
data: {
  deletedAt: new Date();
}
// อ่านปกติ ต้องกรองเสมอ
where: {
  deletedAt: null;
}
```

ได้ถังขยะ 30 วันและการกู้คืน ⚠️ ราคาที่จ่ายคือ **ทุก query ต้องจำใส่ `deletedAt: null`**
ลืมเมื่อไรผู้ใช้จะเห็นของที่ลบไปแล้ว — เป็นเหตุผลหนึ่งที่เรารวม query ไว้ใน service เดียว

### เก็บ UTC เสมอ

ฐานข้อมูลเก็บเวลาเป็น UTC ล้วน การแปลงเป็นเวลาท้องถิ่นทำที่ application layer เท่านั้น

เหตุผล: ผู้ใช้เดินทางข้ามโซนเวลา, เซิร์ฟเวอร์อยู่คนละประเทศ, DST ทำให้เวลาบางค่า
เกิดสองครั้งหรือไม่เกิดเลยในหนึ่งปี ถ้าเก็บเวลาท้องถิ่นลง DB คุณจะไม่มีทางรู้ว่า
"01:30 ของวันนั้น" หมายถึงก่อนหรือหลังปรับเวลา

📁 `packages/core/src/time.ts` มีฟังก์ชันแปลงที่ทดสอบ DST จริง
(ดูเทสต์ `packages/core/src/time.test.ts` เคส `America/New_York`)

### เงินเป็นจำนวนเต็มหน่วยย่อย

`125.50 บาท` เก็บเป็น `12550` (สตางค์)

เพราะ `0.1 + 0.2 !== 0.3` ในเลขทศนิยมฐานสอง — ลองพิมพ์ใน console ดูได้
ยอดที่คลาดเคลื่อนเศษสตางค์สะสมคือบั๊กที่ตรวจสอบย้อนหลังยากมาก

### แยก `occurredAt` ออกจาก `createdAt`

- `createdAt` = ตอนบันทึกลงระบบ
- `occurredAt` = ตอนที่เหตุการณ์นั้น "เป็นของ"

จำเป็นสำหรับ offline sync: บันทึกค่ากาแฟตอนเน็ตหลุดเมื่อวาน แล้ว sync วันนี้
`createdAt` คือวันนี้ แต่รายจ่ายต้องไปอยู่ในยอดของเมื่อวาน

## 6. Transaction และ ACID

**Transaction** = กลุ่มคำสั่งที่ต้องสำเร็จทั้งหมดหรือไม่สำเร็จเลย

```ts
await this.prisma.$transaction([
  this.prisma.user.update({ ... }),        // เปลี่ยนรหัสผ่าน
  this.prisma.session.updateMany({ ... }), // เพิกถอนทุก session
]);
```

📁 `apps/api/src/auth/auth.service.ts` → `resetPassword()`

ถ้าไม่ใช้ transaction แล้วคำสั่งที่สองพัง จะได้สถานะที่อันตราย:
รหัสผ่านเปลี่ยนแล้วแต่ session เก่าของผู้บุกรุกยังใช้ได้อยู่

**ACID** คือสมบัติที่ฐานข้อมูลเชิงสัมพันธ์รับประกัน:

- **A**tomicity — ทั้งหมดหรือไม่เลย
- **C**onsistency — ข้อมูลยังถูกต้องตาม constraint เสมอ
- **I**solation — transaction ที่รันพร้อมกันไม่เห็นสถานะครึ่ง ๆ กลาง ๆ ของกันและกัน
- **D**urability — ตอบว่าสำเร็จแล้วไฟดับ ข้อมูลยังอยู่

## 7. ORM คืออะไร และ Prisma ทำงานอย่างไร

**ORM (Object-Relational Mapper)** แปลงระหว่างตารางในฐานข้อมูลกับ object ในภาษาโปรแกรม
เขียน `prisma.entry.findMany({ where: { userId } })` แทน SQL ดิบ

ได้อะไร: type safety, กัน SQL injection โดยอัตโนมัติ, ระบบ migration
เสียอะไร: ควบคุม SQL ได้น้อยลง, query ซับซ้อนมาก ๆ อาจต้องเขียน raw SQL อยู่ดี

### วงจรการทำงานของ Prisma

```
1. เขียน schema.prisma            ← แหล่งความจริงเดียวของโครงสร้างข้อมูล
2. pnpm db:migrate --name init    ← Prisma สร้างไฟล์ SQL + รันกับ DB
3. pnpm db:generate               ← สร้าง TypeScript client ที่รู้จักทุกตาราง/คอลัมน์
4. import { PrismaClient }        ← เขียนโค้ดโดยมี autocomplete ครบ
```

⚠️ **ต้องรัน `db:generate` ทุกครั้งที่แก้ schema** ไม่งั้น type จะไม่ตรงกับของจริง
และเป็นเหตุผลที่ `.github/actions/setup` รันคำสั่งนี้ให้ทุก job

### Migration คืออะไร

ไฟล์ SQL ที่เรียงตามเวลา บันทึกว่าโครงสร้างเปลี่ยนอย่างไรทีละขั้น

```
prisma/migrations/
  20260918120000_init/migration.sql
  20260918130000_custom_indexes/migration.sql
```

ฐานข้อมูลจะมีตาราง `_prisma_migrations` จำว่ารันอันไหนไปแล้ว
`prisma migrate deploy` (ใช้บน production/CI) จะรันเฉพาะอันที่ยังไม่เคยรัน

**ทำไมห้ามแก้ไฟล์ migration ที่ถูกใช้ไปแล้ว:** เครื่องคนอื่นรันเวอร์ชันเก่าไปแล้ว
ถ้าแก้ย้อนหลัง โครงสร้างจะไม่ตรงกันโดยไม่มีใครรู้ → ให้สร้าง migration ใหม่เสมอ

### Zero-downtime migration (ความรู้ล่วงหน้าที่ควรมี)

ตอน deploy จะมีช่วงที่ **โค้ดเก่ากับโค้ดใหม่รันพร้อมกัน** ถ้า migration ลบคอลัมน์ทิ้งทันที
โค้ดเก่าจะพัง วิธีที่ปลอดภัยคือทำเป็น 3 ขั้นข้าม deploy:

```
1. เพิ่มคอลัมน์ใหม่ (nullable)  → โค้ดใหม่เขียนทั้งสองที่
2. ย้ายข้อมูลเก่า               → โค้ดใหม่อ่านจากคอลัมน์ใหม่
3. ลบคอลัมน์เก่า                → deploy ถัดไปค่อยลบ
```

### Prisma client extension — เกราะกัน IDOR ชั้นที่สอง

📁 `apps/api/src/infra/prisma/prisma.service.ts` → `forUser(userId)`

```ts
if (READ_WRITE_OPS.has(operation)) {
  a.where = { ...(a.where ?? {}), userId }; // เติมให้อัตโนมัติ
}
```

ต่อให้ service ลืมใส่ `where: { userId }` สักที่ extension นี้เติมให้
= ต้องพลาดสองชั้นพร้อมกันถึงจะทำข้อมูลรั่ว (หลักการ defense in depth)

### ปัญหา N+1 (ต้องรู้จัก)

```ts
const entries = await prisma.entry.findMany();          // 1 query
for (const e of entries) {
  const tags = await prisma.entryTag.findMany({ ... }); // อีก N query!
}
```

100 แถว = 101 query → ช้ามาก
แก้ด้วยการบอกให้ดึงมาพร้อมกันตั้งแต่แรก:

```ts
findMany({ include: { tags: { include: { tag: true } } } }); // 2 query
```

📁 `apps/api/src/entries/entries.service.ts` → `INCLUDE_RELATIONS`

### Connection pool

การเปิดการเชื่อมต่อใหม่ทุกคำขอช้ามาก ORM จึงเปิดไว้จำนวนหนึ่งแล้วหมุนเวียนใช้
⚠️ ถ้าตั้ง pool ใหญ่เกินกว่าที่ PostgreSQL รับได้ (`max_connections`) จะพังตอนโหลดสูง
ค่านี้อยู่ที่ `DATABASE_POOL_SIZE` ใน 📁 `.env.example`

## แบบฝึกหัดท้ายบท

1. เปิด Prisma Studio (`pnpm db:studio`) ดูข้อมูลที่ seed ไว้ แล้วลองแก้ค่าใน payload ของ entry
   ผ่าน UI — สังเกตว่าฐานข้อมูล **ไม่ห้าม** แม้จะผิด schema ของ Zod (นั่นคือข้อแลกเปลี่ยนของ JSONB)
2. ตอบให้ได้ว่าทำไม `@@index([userId, status, occurredAt])` ถึงช่วย query
   "งานที่ยังไม่เสร็จของฉัน เรียงตามกำหนดส่ง" แต่ index `[status]` เดี่ยว ๆ แทบไม่ช่วยเลย
3. ลองเขียน query ที่ทำให้เกิด N+1 แล้วแก้ด้วย `include`
4. อ่าน 📁 `apps/api/prisma/sql/custom_indexes.sql` แล้วอธิบายให้ได้ว่า
   ทำไม partial index ถึงเล็กกว่า index ปกติมาก
