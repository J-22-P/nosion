## 1. เงินต้องเป็นจำนวนเต็ม

### 1.1 ปัญหา: คอมพิวเตอร์เก็บ 0.1 ไม่ได้พอดี

```js
0.1 + 0.2; // 0.30000000000000004
```

`number` ของ JavaScript คือ **IEEE 754 double** — เก็บเลขฐานสอง 0.1 ในฐานสองเป็นทศนิยมไม่รู้จบ
(เหมือน 1/3 = 0.333… ในฐานสิบ) จึงถูกปัดตั้งแต่ตอนเก็บ ความคลาดเล็กมาก แต่ **บวกสะสม** หลายร้อยรายการ
ยอดรวมจะคลาดทีละสตางค์ และการเทียบ `===` จะผิดทันที

### 1.2 ทางแก้: เก็บเป็น "หน่วยย่อย" (minor unit)

| เงิน       | เก็บเป็น `amountMinor` |
| ---------- | ---------------------- |
| ฿65        | `6500`                 |
| ฿125.50    | `12550`                |
| ¥500 (เยน) | `500` — เยนไม่มีทศนิยม |

จำนวนเต็มบวกลบกันได้แม่นยำเสมอ (ถึง `Number.MAX_SAFE_INTEGER` ≈ 9 พันล้านล้าน — พอสำหรับเงินบุคคล)
ทศนิยมเกิดขึ้น **ตอนแสดงผลเท่านั้น**

📁 `packages/contracts/src/payloads.ts` — `amountMinor: z.number().int()` · API ปฏิเสธ `65.5` ด้วย 422

### 1.3 แปลงข้อความ → หน่วยย่อย โดยไม่ผ่าน float

📁 `packages/core/src/money.ts` → `parseAmountToMinor`

```ts
// "1,250.75" → ต่อสตริง "1250" + "75" → Number("125075")
const minor = Number(whole + fraction.padEnd(digits, '0'));
```

⚠️ วิธีที่ดูง่ายกว่า `Math.round(parseFloat(text) * 100)` **ใช้ได้เกือบทุกกรณี** แต่ "เกือบ" คือปัญหา —
`1.005 * 100 = 100.49999999999999` → ปัดได้ 100 ไม่ใช่ 101 · การต่อสตริงไม่มีขั้นตอนไหนเป็น float เลย

ทศนิยมของแต่ละสกุลอ่านจาก `Intl.NumberFormat(…).resolvedOptions().maximumFractionDigits` —
ไม่ต้องดูแลตาราง "THB=2, JPY=0" เอง

### 1.4 แสดงผล

`formatMoney(842000, 'THB', { decimals: false })` → `฿8,420` (KPI) · `formatMoney(79900)` → `฿799.00` (ตาราง/บิล)
ตามสเปก 8.11.3 · ใช้ `Intl.NumberFormat('th-TH', { style: 'currency' })` ซึ่งรู้เองว่าสัญลักษณ์อยู่หน้า และใส่ลูกน้ำทุกสามหลัก

🎤 _"ทำไมไม่ใช้ `DECIMAL` ในฐานข้อมูล"_ → ใช้ได้ (Postgres `NUMERIC` แม่นยำ) แต่พอข้อมูลออกมาเป็น JSON
แล้วเข้า JavaScript ก็กลายเป็น `number` (float) อีก · เราเก็บใน JSONB ด้วย จึงเลือก integer ตลอดทาง
ทุกชั้นพูดภาษาเดียวกัน ไม่มีจุดไหนต้องแปลง

## 2. "เดือนนี้" เริ่มตอนไหน

### 2.1 ปัญหา

ฐานข้อมูลเก็บเวลาเป็น UTC (บท 13) แต่ "เดือนกันยายน" ของคนไทยเริ่ม **1 ก.ย. 00:00 เวลาไทย**
ซึ่งตรงกับ **31 ส.ค. 17:00 UTC** — ถ้า query ด้วย `>= '2026-09-01T00:00Z'`
รายจ่ายมื้อเช้าวันที่ 1 (ก่อน 07:00) จะหลุดไปอยู่เดือนสิงหาคม

### 2.2 ทางแก้: หาขอบเดือนจาก "หน้าปัด" ของผู้ใช้

📁 `packages/core/src/time.ts` → `monthBoundsInTimeZone` / `periodBounds`

```ts
start: zonedTimeToUtc(`${year}-${pad(month)}-01T00:00:00`, timeZone),
end:   zonedTimeToUtc(`${next.y}-${pad(next.m)}-01T00:00:00`, timeZone), // ต้นเดือนถัดไป (exclusive)
```

- ใช้ `[start, end)` แบบเดียวกับ "วันนี้" ในบท 13 — ต้นเดือนถัดไปเป็นขอบ **ไม่รวม** จึงไม่มีรายการไหนนับซ้ำสองเดือน
- **ไม่** คำนวณ `end = start + จำนวนวัน × 24 ชม.` — เดือนที่มี DST (มี.ค. ของ New York) ยาว 30 วัน 23 ชม.
  เทสต์ `periodBounds('2026-03', 'America/New_York')` จับเรื่องนี้ไว้
- `periodBounds(period, tz, shift)` เลื่อนเดือนด้วยเลขคณิต `ปี×12 + เดือน` — ข้ามปีได้โดยไม่มี if (ใช้ทำกราฟย้อนหลัง 6 เดือน)
- จำนวนวันในเดือน: `new Date(Date.UTC(year, month, 0)).getUTCDate()` — "วันที่ 0 ของเดือนถัดไป" คือวันสุดท้ายของเดือนนี้

## 3. โมดูลที่สอง — พิสูจน์ plugin architecture

### 3.1 สิ่งที่ต้องเขียน vs สิ่งที่ต้องแก้

| ไฟล์                                               | ทำอะไร                                            |
| -------------------------------------------------- | ------------------------------------------------- |
| 📁 `modules/expense/expense.trackable.ts` _(ใหม่)_ | implement `TrackableModule` + `@RegisterModule()` |
| 📁 `modules/expense/expense.module.ts` _(ใหม่)_    | NestJS module                                     |
| 📁 `app.module.ts` _(แก้ 2 บรรทัด)_                | import + ใส่ในรายการ                              |
| `entries/`, `core/registry/`, Today, Calendar      | **ไม่แตะเลย**                                     |

ทันทีที่ลงทะเบียน `POST /entries { module: 'expense' }` ใช้ได้ — เพราะ entries service ถาม registry ว่ามีโมดูลนี้ไหม
แล้วใช้ `payloadSchema` ของโมดูลนั้น validate (เทสต์ `expenses.int-spec.ts` พิสูจน์ข้อนี้)
ก่อนหน้านี้ `module: 'expense'` ได้ error "unknown module" ทั้งที่ schema มีอยู่ใน contracts แล้ว

### 3.2 กฎทางธุรกิจอยู่ในฟังก์ชันเดียว

"ใช้จ่ายจริง" นับอะไรบ้าง — ตัดสินที่ `isSpent()` ที่เดียว:

| รายการ                     | นับ? | เหตุผล                                           |
| -------------------------- | ---- | ------------------------------------------------ |
| รายจ่ายทั่วไป              | ✅   |                                                  |
| รายรับ                     | ❌   | คนละทิศ                                          |
| ยกเลิกแล้ว / ลบแล้ว        | ❌   |                                                  |
| บิลที่ยังไม่จ่าย (pending) | ❌   | ยังไม่ได้เสียเงิน — เป็น "ภาระ" ไม่ใช่ "รายจ่าย" |

## 4. Parser แบบ rule-based: "กาแฟ 65"

### 4.1 ทำไมไม่ใช้ LLM

สเปก 6.4: ช้า (หลายร้อย ms), มีค่าใช้จ่ายต่อครั้ง, ผลไม่แน่นอน (เทสต์ยาก) — ข้อความสั้นแบบนี้มีโครงสร้างพอให้ regex จับได้
แต่ละโมดูลลอง parse เอง แล้วคืน `confidence` ให้ตัวกลาง (Phase 5) เลือกตัวที่มั่นใจที่สุด

### 4.2 โครงของ regex

📁 `apps/api/src/modules/expense/expense-text.ts`

```
^(?<title>.+?)  \s+  ฿?\s*(?<amount>ตัวเลข)  \s*(?<unit>บาท|฿|thb)?  (?:\s+(?<rest>.*))?$
 "กาแฟ"               "65"                        "บาท"                    "ทุกวันที่ 5"
```

- **named group** `(?<title>…)` อ่านง่ายกว่า `m[1]` และไม่พังเมื่อเพิ่มวงเล็บ
- `.+?` (lazy) — กินให้น้อยที่สุด ไม่งั้น `.+` จะกลืน "ค่าเน็ต 799 ทุกวันที่" แล้วเหลือแค่ "5" เป็นจำนวนเงิน
- ต้องมี **ช่องว่าง** หน้าตัวเลข → `ais5g` ไม่ถูกตีเป็นเงิน 5 บาท

### 4.3 กับดัก: substring ซ้อนกัน → "คำที่ยาวที่สุดชนะ"

```
"ค่าน้ำมัน"  มี  "ค่าน้ำ" (สาธารณูปโภค)  และ  "น้ำมัน" (เดินทาง)  อยู่ข้างใน
"หนังสือ"   มี  "หนัง" (บันเทิง)
```

ถ้าใช้ "เจอคำแรกในรายการ" ผลขึ้นกับลำดับที่เขียนพจนานุกรม — แก้ลำดับทีหนึ่ง อีกเคสพัง
`guessCategory` เลือก **keyword ที่ยาวที่สุด** ที่พบ แล้วใส่คำเต็ม "ค่าน้ำมัน" ไว้ในหมวดเดินทาง
→ กฎเดียว ไม่ขึ้นกับลำดับ (นี่คือหลัก longest match แบบเดียวกับที่ lexer ของภาษาโปรแกรมใช้: `>=` ต้องไม่ถูกอ่านเป็น `>` กับ `=`)

### 4.4 Table-driven test

```ts
const CASES = [
  { input: 'กาแฟ 65', title: 'กาแฟ', amountMinor: 6500, category: 'food' },
  { input: 'ค่าน้ำมัน 1,200', title: 'ค่าน้ำมัน', amountMinor: 120000, category: 'transport' },
  …
];
it.each(CASES)('"$input"', …);
```

เพิ่มเคสที่ผู้ใช้เจอจริง = เพิ่ม 1 บรรทัด · ชื่อเทสต์คือ input เอง เวลาล้มรู้ทันทีว่าประโยคไหน

### 4.5 วันครบกำหนดของ "ทุกวันที่ 31"

`nextDueDate(31, …)` ในเดือนที่มี 30 วัน → วันที่ 30 (clamp ไปวันสุดท้าย) ไม่ใช่ข้ามไปเดือนถัดไป
เหมือนที่ธนาคารตัดบัตรเครดิต · rrule เต็มรูปแบบมาใน Phase 3

## 5. งบประมาณ: NULL, partial index และ "กฎที่เดียว"

### 5.1 NULL ไม่เท่ากับ NULL

SQL ใช้ **ตรรกะสามค่า**: `TRUE`, `FALSE` และ `UNKNOWN` · NULL แปลว่า "ไม่รู้ค่า" —
"ค่าที่ไม่รู้ เท่ากับ ค่าที่ไม่รู้ไหม?" คำตอบคือ "ไม่รู้" (`UNKNOWN`) ไม่ใช่ `TRUE`

```sql
SELECT NULL = NULL;   -- NULL (ไม่ใช่ true)
SELECT NULL IS NULL;  -- true  ← ต้องใช้ IS เสมอ
```

unique constraint ถือว่าสองแถว "ซ้ำ" ก็ต่อเมื่อเทียบแล้วได้ `TRUE` → แถวที่มี NULL **ไม่ซ้ำกับใครเลย**

```
budgets UNIQUE ("userId", "category", "period")
  (alice, 'food', 'monthly')  +  (alice, 'food', 'monthly')  → ❌ ชน
  (alice,  NULL,  'monthly')  +  (alice,  NULL,  'monthly')  → ✅ ผ่านทั้งคู่ ← งบรวมสองก้อน
```

เราเจอเรื่องนี้ตอนเขียน endpoint งบประมาณ — ลอง INSERT จริงในฐานเทสต์ (ใน transaction แล้ว ROLLBACK) ได้สองแถว
ถ้าไม่ลอง จะรู้ตัวเมื่อหน้า Expenses แสดงงบรวมผิดเพราะ `findFirst` สุ่มได้คนละก้อน

### 5.2 ทางแก้: partial unique index

```sql
CREATE UNIQUE INDEX "budgets_one_total_per_user_period"
  ON "budgets" ("userId", "period")
  WHERE "category" IS NULL;
```

index นี้มีเฉพาะแถวที่ `category IS NULL` และไม่มีคอลัมน์ `category` ใน key เลย → ปัญหา NULL หายไป
เทคนิคเดียวกับ `focus_sessions_one_running_per_user` (บท 13 หัวข้อ 7) — "unique เฉพาะบางแถว"

ทางเลือกอื่น: Postgres 15+ มี `UNIQUE NULLS NOT DISTINCT` แต่ประกาศใน `schema.prisma` ไม่ได้
ส่วน partial index เราตรวจแล้วว่า `prisma migrate diff` ไม่นับเป็น drift

📁 `budgets.service.ts` จับ `P2002` (unique violation) แปลงเป็น **409** พร้อมข้อความว่าชนเพราะอะไร —
ไม่ `findFirst` ก่อนแล้วค่อย `create` เพราะสองคำขอพร้อมกันจะผ่านการเช็คทั้งคู่ (TOCTOU, บท 13)

🎤 _"unique constraint กับคอลัมน์ที่ nullable ทำงานอย่างไร"_ → NULL ไม่ชนกัน · ถ้าต้องการ "ได้ NULL แถวเดียว"
ใช้ partial unique index หรือ `NULLS NOT DISTINCT` · และอย่าเช็คด้วย SELECT ก่อน INSERT

### 5.3 รวมยอดที่ไหน: SQL หรือโค้ด

| ทาง                                                | ข้อดี                                      | ข้อเสีย                                                             |
| -------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| `SELECT payload->>'category', SUM(...) GROUP BY 1` | เร็ว ส่งข้อมูลน้อย                         | กฎ "ใช้จ่ายจริง" (ไม่นับรายรับ/บิลค้าง/ยกเลิก) ต้องเขียนซ้ำเป็น SQL |
| ดึงแถวของเดือน แล้วรวมด้วย `isSpent()`             | **กฎอยู่ที่เดียว** ทดสอบด้วย unit test ได้ | ส่งแถวมามากกว่า                                                     |

ข้อมูลการเงินของคนหนึ่งคนต่อเดือนมีหลักร้อยแถว → เลือกทางที่สอง
ถ้าวันหนึ่งกฎเปลี่ยน (เช่น "ไม่นับเงินออม") แก้ที่ `isSpent()` แล้ว Today, Weekly, งบ, คาดการณ์ ตรงกันหมดทันที

📌 เลือก "ถูกต้องและแก้ที่เดียว" ก่อน "เร็ว" — แล้ว **จดไว้ว่าจะเปลี่ยนเมื่อไร** (ในโค้ด: "ถ้าเกินหลักหมื่นค่อยย้ายเป็น raw SQL")

### 5.4 กฎสีอยู่ใน contracts

`budgetTone(spent, limit)` อยู่ใน 📁 `packages/contracts/src/expenses.ts` — API ใช้ตอบ `tone`, web ใช้ระบายสี bar
ถ้า API บอก `warning` แต่ web คำนวณเองได้ `safe` เพราะเขียนเกณฑ์ไม่ตรงกัน ผู้ใช้จะเห็น chip "ใกล้เกิน" คู่กับ bar สีปกติ
เทสต์ขอบ: 85% พอดี = warning · 100% พอดี = over · งบ 0 = safe (ไม่หารด้วยศูนย์)

## 6. คาดการณ์และบิล — ตัวเลขที่ "อธิบายได้"

### 6.1 Run-rate forecast

วิธีที่ง่ายที่สุดที่ยังมีประโยชน์: **"ใช้ในอัตรานี้ต่อไป สิ้นเดือนจะเป็นเท่าไร"**

```
วันที่ 18 จาก 30 วัน · ใช้ไปแล้ว ฿5,400 (จร)
อัตรา = 5,400 ÷ 18 = ฿300/วัน  →  สิ้นเดือน ≈ 300 × 30 = ฿9,000
```

แต่ถ้าเอายอดทั้งหมดมาคูณ จะพังทันทีกับค่าใช้จ่าย **ก้อนเดียวต่อเดือน**:

```
วันที่ 1 จ่ายค่าเช่า ฿8,500  →  8,500 ÷ 1 × 30 = ฿255,000  ❌
```

จึงแยกสามส่วน (📁 `expense-analytics.ts` → `buildForecast`):

| ส่วน              | ทำอย่างไร         | เหตุผล                               |
| ----------------- | ----------------- | ------------------------------------ |
| variable (จร)     | ขยายตามสัดส่วนวัน | เกิดสม่ำเสมอตามเวลา                  |
| fixed ที่จ่ายแล้ว | บวกตรง ๆ          | เกิดครั้งเดียว ไม่เกิดซ้ำในเดือนนี้  |
| บิลที่ยังไม่จ่าย  | บวกตรง ๆ          | **รู้อยู่แล้ว** ว่าจะมา — ไม่ต้องเดา |

นี่คือเหตุผลที่ payload มี `costType` ตั้งแต่ Phase 0 — ไม่ใช่แค่ป้ายบนตาราง แต่เปลี่ยนวิธีคำนวณ

⚠️ ต้นเดือนตัวเลขแกว่ง: วันที่ 1 กินข้าวมื้อละ ฿500 ครั้งเดียว → คาดการณ์ ฿15,000
ยอมรับไว้เพราะสูตรอธิบายผู้ใช้ได้ในประโยคเดียว · ทางแก้ภายหลังคือผสมกับค่าเฉลี่ยเดือนก่อนแบบถ่วงน้ำหนัก

🎤 _"ทำไมไม่ใช้ ML"_ → ข้อมูลของผู้ใช้ใหม่มีไม่กี่สิบแถว, ผู้ใช้ต้อง **เชื่อ** ตัวเลขถึงจะปรับพฤติกรรม —
สูตรที่อธิบายได้ ("ใช้วันละ ฿300 อีก 12 วัน + บิลค่าเน็ต") ชนะโมเดลที่แม่นกว่า 5% แต่อธิบายไม่ได้

### 6.2 แบ่งถังตามเวลา (bucketing)

กราฟ 6 เดือนต้องการ "ยอดต่อเดือน" — ทางที่ช้า: query 6 ครั้ง · ทางที่ใช้: query **ครั้งเดียว** ทั้งช่วง
แล้วโยนแต่ละรายการลงถังด้วย `monthBoundsInTimeZone(date, tz).period`

สองกับดักที่เทสต์คุมไว้:

1. **เดือนที่ไม่มีรายการต้องได้ศูนย์ ไม่ใช่หายไป** — สร้างถังจากรายการเดือนก่อน แล้วค่อยเติม ไม่ใช่สร้างถังจากรายการที่มี
   (ไม่งั้นกราฟจะลากเส้นตรงจากกรกฎาคมไปกันยายน เหมือนสิงหาคมไม่มีอยู่)
2. **ถังต้องตัดตามโซนเวลาผู้ใช้** — รายการ 31 ส.ค. 18:00 UTC เป็นของเดือนกันยายนสำหรับคนไทย

### 6.3 วันปฏิทิน ไม่ใช่ 24 ชั่วโมง

"บิลครบกำหนดอีกกี่วัน" — ถ้าคำนวณ `(due − now) ÷ 86,400,000` ตอน 22:00 กับ 08:00 จะได้คนละค่า
และในวันที่ DST เปลี่ยน วันหนึ่งยาว 23 ชม. · `daysBetween('2026-09-18', '2026-09-20')` เทียบ **วันที่ล้วน**
(แปลงเป็น `Date.UTC` ของเที่ยงคืนแล้วลบกัน) → 2 เสมอ ไม่ว่าตอนนี้กี่โมง

### 6.4 กรองใน JSONB ด้วย Prisma

`isBill` อยู่ใน `payload` (JSONB) ไม่ใช่คอลัมน์:

```ts
payload: { path: ['isBill'], equals: true }   // → WHERE payload #> '{isBill}' = 'true'
```

ตัวนี้ **unit test พิสูจน์ไม่ได้** (ไม่มีฐานข้อมูล) — integration test สร้างบิล + กาแฟที่ไม่ใช่บิล แล้วยืนยันว่ากาแฟไม่โผล่
บิลค้างจ่ายจากเดือนก่อนยังต้องอยู่ (`OR: [{ เดือนนี้ }, { ก่อนเดือนนี้ AND ยังไม่จ่าย }]`) — ไม่งั้นบิลที่ลืมจ่ายจะหายไปเงียบ ๆ ตอนขึ้นเดือนใหม่

### 6.5 เทสต์ที่ไม่ขึ้นกับวันที่รัน

integration test เรียก endpoint ที่ใช้ "ตอนนี้" จริง (forecast, bills) — ถ้าเขียน `expect(dueSoonCount).toBe(2)`
พร้อมบิลอีก 2 วัน เทสต์จะแดงทุกวันที่ 29–31 เพราะบิลข้ามไปเดือนหน้า

ทางแก้: เลือกข้อมูลที่ **ไม่มีทางข้ามขอบ** (บิล "วันนี้" อยู่ในเดือนนี้เสมอ, บิล "40 วันก่อน" อยู่เดือนก่อนเสมอ)
และ assert เป็นความสัมพันธ์ (`fixedMonthlyMinor` = ผลรวมบิลที่ `dueDate` ขึ้นต้นด้วยเดือนนี้) แทนตัวเลขตายตัว
ส่วนตัวเลขแม่น ๆ ทดสอบใน unit test ที่ตรึงเวลาด้วย `NOW` ได้

## 7. หน้า Today: รวมทุกโมดูลโดยไม่รู้จักโมดูลไหน

### 7.1 Aggregator บน registry

📁 `apps/api/src/entries/today/today.service.ts`

```ts
const modules = this.registry.all(ctx.enabledModules);          // เฉพาะที่ผู้ใช้เปิด
const rows = await prisma.entry.findMany({ … module: { in: keys } … });
const settled = await Promise.allSettled(
  modules.map(async (m) => m.summarizeToday(byModule.get(m.key) ?? [], ctx)),
);
```

ไม่มีคำว่า `task` หรือ `expense` ในไฟล์นี้เลย — เทสต์ "ปิดโมดูลใน settings → การ์ดหาย" พิสูจน์ว่าวนตาม registry จริง
core ส่ง entries ที่ "เกี่ยวกับวันนี้" แบบกว้าง ๆ (เกิดวันนี้ / ค้างจากวันก่อน / เสร็จวันนี้) แล้วให้ **โมดูลตีความเอง** —
งานที่ค้างคือ "เลยกำหนด" แต่บิลที่ค้างไม่ใช่ "รายจ่ายวันนี้"

### 7.2 MaybePromise — เมื่อ interface ในสเปกเล็กไป

สเปกเขียน `summarizeToday(): TodayWidget` (sync) แต่การ์ดการเงินต้องรู้ยอดทั้งเดือนเทียบงบ ซึ่งไม่อยู่ใน entries ของวันนี้

| ทางเลือก                                          | ปัญหา                                                          |
| ------------------------------------------------- | -------------------------------------------------------------- |
| TodayService ดึงงบให้                             | core ต้องรู้จัก "งบ" → ผิดกฎข้อ 1 · เพิ่มโมดูลใหม่ต้องแก้ core |
| หน้าเว็บยิง /today + /budgets/status + /bills เอง | เสีย "คำขอเดียว" และหน้าเว็บต้องรู้จักโมดูล                    |
| **ให้คืน `TodayWidget \| Promise<TodayWidget>`**  | โมดูลดึงข้อมูลเองผ่าน DI · core แค่ `await`                    |

`TodayWidget | Promise<TodayWidget>` (เรียกว่า **MaybePromise**) ทำให้โมดูลเดิมที่ sync ไม่ต้องแก้สักบรรทัด —
`await` ค่าที่ไม่ใช่ Promise ได้ค่าเดิมกลับมา · ข้อเสีย: ต้อง `await` ทุกที่ที่เรียก (TypeScript บังคับให้เอง)

### 7.3 Partial failure ด้วย `Promise.allSettled`

|                 | `Promise.all`             | `Promise.allSettled`                                |
| --------------- | ------------------------- | --------------------------------------------------- |
| ตัวหนึ่ง reject | ทั้งก้อน reject ทันที     | ได้ผลครบทุกตัว แต่ละตัวบอก `fulfilled` / `rejected` |
| เหมาะกับ        | ต้องได้ครบถึงจะมีความหมาย | ส่วนต่าง ๆ อิสระต่อกัน                              |

หน้า Today คือกรณีที่สอง: query งบพังไม่ควรทำให้ผู้ใช้มองไม่เห็นงานวันนี้ → ตอบ 200 พร้อม `failedModules: ['expense']`
ให้หน้าเว็บแสดง error เฉพาะการ์ดนั้น (ตรงกับที่สเปก 8.11.1 ให้แต่ละการ์ดมี Suspense ของตัวเอง)

### 7.4 Lint เป็นสถาปนิกที่ไม่เคยลืม

ครั้งแรกวาง TodayService ไว้ใน `core/today/` — ฟังดูถูก ("Today เป็นของกลาง") แต่ lint แดงสองกฎ:

```
'@prisma/client' import is restricted … core/ ทำงานกับ domain type เท่านั้น
No rule allowing this dependency was found. File is of type 'core'. Dependency is of type 'entries'
```

กฎเขียนไว้ตั้งแต่ Phase 0 (บท 05) และ **จับได้ก่อนรีวิว** · คำตอบอยู่ใน config เอง: ชั้น `entries/` นิยามว่า
"ทำงานกับโมดูลผ่าน registry เท่านั้น" — ตรงกับงานของ Today พอดี จึงย้ายไป `entries/today/`

### 7.5 ค่าที่คำนวณ ไม่ต้องเก็บ: Blocked ใน standup

สเปกไม่เพิ่ม status `blocked` — งานติดอยู่ = ยังไม่เสร็จ **และ** (มี dependency ที่ยังไม่จบ **หรือ** แท็ก `#blocked`)
ถ้าเก็บเป็น status ต้องคอยอัปเดตทุกครั้งที่งานต้นทางเสร็จ (ลืมเมื่อไรข้อมูลเพี้ยน) · คำนวณตอนอ่านจึงถูกเสมอ
นี่คือหลักเดียวกับ "derived state" ใน React (บท 12) — อย่าเก็บสิ่งที่คำนวณจากสิ่งที่เก็บอยู่แล้วได้

### 7.6 Config ที่ไม่ error ≠ config ที่ทำงาน

`fileParallelism: false` ใน `projects[]` ของ vitest 3 **ถูกเมินเงียบ ๆ** (บท 08) — integration test รันขนานกันมาตั้งแต่ Phase 1
โดยที่ทุกคนเชื่อว่ารันทีละไฟล์ จนเพิ่มไฟล์ที่ 5 แล้วเจอ deadlock · วิธีพิสูจน์ด้วยตัวเลข ไม่ต้องเชื่อ config:
**ผลรวมเวลาของแต่ละไฟล์ > เวลารวมของทั้งชุด = รันขนานแน่นอน**

📌 ทุกครั้งที่ตั้ง option เพื่อ "กัน" อะไร ให้หาวิธีเห็นผลของมัน — ไม่ใช่แค่ไม่มี error

🎤 _"เคยเจอเทสต์ flaky ไหม แก้อย่างไร"_ → เรื่องนี้ครบทุกขั้น: อาการสุ่ม → อ่าน log ฐานข้อมูลเจอ 40P01 →
ตั้งสมมติฐาน "รันขนาน" → พิสูจน์ด้วยเวลา → หาว่า config ถูกเมินเพราะอะไร (อ่าน type ของ vitest) → แก้ → รันซ้ำหลายรอบ →
แยกความล้มที่เหลือว่าเป็นของสภาพแวดล้อม (Docker บน Mac) ไม่ใช่ของโค้ด

## 8. "2026-10-01" ไม่ใช่จุดเวลา — บั๊กที่อยู่ในภาพ baseline มาตลอด

### 8.1 สองชนิดของ "เวลา"

| ชนิด                         | ตัวอย่าง                    | ความหมาย                    | แปลงเป็น Date ได้เมื่อ     |
| ---------------------------- | --------------------------- | --------------------------- | -------------------------- |
| instant (จุดเวลา)            | `2026-10-01T10:00:00+07:00` | ช่วงเวลาเดียวกันทั่วโลก     | ได้ทันที                   |
| local date (วันที่ตามปฏิทิน) | `2026-10-01`                | "วันที่ 1" ของ **ใครบางคน** | ต้องรู้ว่าคนนั้นอยู่โซนไหน |

บท 13 แยก instant กับ "หน้าปัด" ไว้แล้ว — วันกำหนดของงานทั้งวันคือหน้าปัด ไม่ใช่ instant

### 8.2 กับดักของ JavaScript

```js
new Date('2026-10-01'); // 2026-10-01T00:00:00.000Z   ← date ล้วน = UTC
new Date('2026-10-01T00:00:00'); // 2026-09-30T17:00:00.000Z   ← มีเวลาไม่มี offset = เวลาเครื่อง (ไทย)
```

สเปก ECMAScript ตีความสองรูปแบบนี้ **ต่างกัน** · โค้ดเดิมใช้แบบแรก → วันกำหนด "1 ต.ค." กลายเป็น 07:00 ของ 1 ต.ค. ตามเวลาไทย
และสำหรับคนในนิวยอร์ก กลายเป็น 20:00 ของ **30 ก.ย.** — งานไปอยู่ผิดวัน

ทางแก้: contracts **ไม่แปลง** date ล้วน (เพราะไม่รู้ว่าเป็นของใคร) · service ที่รู้ timezone ผู้ใช้เรียก
`resolveDateInput('2026-10-01', 'Asia/Bangkok')` → `2026-09-30T17:00:00Z` (00:00 ไทยจริง)

### 8.3 "เลยกำหนด" ของงานทั้งวัน

งานทั้งวันที่กำหนดวันนี้ = ทำเมื่อไรก็ได้ในวันนี้ → **ยังไม่เลยจนกว่าวันจะจบ**

```ts
isAllDay
  ? dayEnd(occurredAt, tz) <= now // จบวันแล้ว
  : occurredAt < now; // เลยเวลาแล้ว
```

ฝั่ง SQL (📁 `common/overdue-where.ts`) แปลงเป็น `occurredAt < ต้นวันนี้` สำหรับงานทั้งวัน — เพราะ occurredAt เก็บเป็น 00:00 ของวันกำหนด
"ต้นวันกำหนด < ต้นวันนี้" ⇔ "วันกำหนดจบไปแล้ว" · กฎเดียวกันอยู่ 3 ที่ (core, SQL, web) และมีเทสต์ทั้ง 3 ที่

### 8.4 เทสต์ที่ "ผ่าน" แต่ผิด

สองเทสต์เดิมล็อกพฤติกรรมผิดไว้:

```ts
expect(dateOnly.occurredAt).toBeInstanceOf(Date); // "แปลงเป็น Date เสมอ"
expect(resolveDeferTarget('2026-12-31', base).toISOString()).toBe('2026-12-31T00:00:00.000Z'); // = 07:00 เวลาไทย
```

ทั้งคู่เขียนโดย **ดูว่าโค้ดคืนอะไร แล้วเอาค่านั้นมาใส่ใน expect** — เทสต์แบบนี้ปกป้องบั๊กแทนที่จะจับบั๊ก
คำถามที่ควรถามตอนเขียน expect: _"ผู้ใช้ที่พิมพ์วันที่ 31 ธ.ค. คาดว่าจะได้อะไร"_ ไม่ใช่ _"ฟังก์ชันคืนอะไร"_

และภาพ baseline ที่อนุมัติไปแล้วก็มีบั๊กนี้อยู่ (ป้ายแดง "⚠ วันนี้" บนงานที่กำหนดวันนี้) — mock data ตั้งใจให้งาน "เลยกำหนดตั้งแต่เมื่อวาน"
แต่ค่าจริงคือ 00:00 ของวันนี้ ซึ่งดูเลยกำหนดได้ **เพราะบั๊ก** · visual test จับได้แค่ "ภาพเปลี่ยน" ไม่ได้รู้ว่า "ภาพถูก"
(บท 14 หัวข้อ 2.7: คนต้องดูภาพเสมอ — และต้องดูด้วยคำถามว่าข้อมูลนี้ควรแสดงแบบนี้จริงไหม)

### 8.5 เทสต์ที่ผลขึ้นกับเครื่อง

`formatDueDate` เดิมใช้ `setHours(0,0,0,0)` = เที่ยงคืนตาม **โซนของเครื่องที่รัน** · Mac เป็นเวลาไทย CI เป็น UTC
→ จุดเวลา 06:00 ไทย (23:00 UTC เมื่อวาน) Mac บอก "วันนี้" CI บอก "เมื่อวาน" · แก้ให้เทียบวันด้วยโซนที่ระบุเสมอ แล้วรันเทสต์ซ้ำด้วย
`TZ=UTC pnpm vitest` เพื่อยืนยันว่าผลไม่ขึ้นกับเครื่อง

🎤 _"เล่าบั๊กเรื่อง timezone ที่เคยเจอ"_ → อาการ (งานวันนี้ขึ้นแดงตั้งแต่ 7 โมงเช้า) → ตัวเลข 7 = offset ของไทย → `new Date('YYYY-MM-DD')` เป็น UTC →
แยก "จุดเวลา" กับ "วันที่ตามปฏิทิน" → แก้ที่ชั้นที่รู้ timezone → กฎ "เลยกำหนด" แยกงานทั้งวัน/มีเวลา ใช้ร่วมกัน 3 ที่ →
เจอเทสต์เก่าที่ล็อกบั๊กไว้ และภาพ baseline ที่มีบั๊กอยู่ในนั้น

- แท่งปลายมนแต่โคนเหลี่ยม: `rect rx` มนทั้งสี่มุม จึงวาดเป็น `path` เอง

### 9.2 Preview ที่ล้าสมัย

ผู้ใช้พิมพ์ "กาแฟ 65" → preview โผล่ → พิมพ์ต่อเป็น "กาแฟ 650" แล้วกด ↵ ทันที (ก่อน 250ms) —
ถ้าบันทึกจาก preview ล่าสุดจะได้ ฿65 ไม่ใช่ ฿650 · ทางแก้: preview เก็บ **ข้อความที่ใช้ parse** ไว้ด้วย
ตอนกด ↵ ถ้า `preview.text !== ข้อความตอนนี้` ให้ parse ใหม่ก่อนบันทึก · effect มี `cancelled` กันคำตอบเก่ามาทับคำตอบใหม่

### 9.3 CSV ไม่ใช่แค่ `join(',')`

| ปัญหา                     | ตัวอย่าง                     | แก้                                                        |
| ------------------------- | ---------------------------- | ---------------------------------------------------------- |
| ช่องมี `,` `"` ขึ้นบรรทัด | `ร้าน "เจ๊", สาขา 2`         | ครอบด้วย `"` และ `"` → `""` (RFC 4180)                     |
| Excel อ่านไทยไม่ออก       | `à¸à¸²à¹à¸`                  | ใส่ BOM `\uFEFF` ต้นไฟล์                                   |
| **CSV injection**         | ชื่อรายการ `=HYPERLINK(...)` | ขึ้นต้นด้วย `= + - @` ใส่ `'` นำหน้า (Excel จะรันเป็นสูตร) |
| จำนวนเงินคำนวณไม่ได้      | `฿1,250.00`                  | ส่งออกตัวเลขล้วน `-1250`                                   |

ข้อยกเว้นที่ต้องระวัง: `-145.00` ขึ้นต้นด้วย `-` แต่เป็นตัวเลขจริง — ถ้าใส่ `'` Excel จะมองเป็นข้อความ

### 9.4 Mock data ที่ "ถูก" ไม่ใช่แค่ "มี"

mock ของ visual test ถ้าตัวเลขไม่สอดคล้อง (หมวดรวมกันได้ 7,000 แต่การ์ดบอก 8,420) ภาพ baseline จะสวยแต่ **ผิด** —
คนดูภาพจะเชื่อว่าหน้าคำนวณถูก · จึงคุมว่า ผลรวมหมวด = ยอดเดือน = ผลรวม series รายวัน (ตรวจด้วย node ก่อนสร้างภาพ)
บทเรียนเดียวกับหัวข้อ 8.4: ภาพ baseline มีบั๊กอยู่ได้ ถ้าข้อมูลที่ใช้ถ่ายผิดเอง

### 9.5 Flaky จากโหลดแรก — แยกให้ออกก่อนจะ "แก้ด้วย timeout"

การเพิ่ม timeout มักเป็นการซ่อนบั๊ก · ก่อนเพิ่มเราถามสามข้อ:

1. ทำซ้ำได้ไหมในสภาพปกติ? (Mac 20 รอบ: ไม่เจอ)
2. ล้มที่ขั้นไหน? (รอข้อมูลโผล่ — ไม่ใช่การเทียบภาพ ไม่ใช่ค่าผิด)
3. มีเหตุอธิบายไหม? (โหลดแรกของหน้าที่ยิง API 5 ตัว ใน container ที่รัน 4 worker พร้อมกัน)

ครบสามข้อจึงเพิ่มเวลารอเฉพาะ "หน้าพร้อม" เป็น 15 s แล้วยืนยันด้วย `--retries=0` สองรอบ — ไม่ใช่ปล่อยให้ retry ของ CI กลบไว้
