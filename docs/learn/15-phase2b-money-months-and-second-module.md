## 1. เงินต้องเป็นจำนวนเต็ม

### 1.1 ปัญหา: คอมพิวเตอร์เก็บ 0.1 ไม่ได้พอดี

```js
0.1 + 0.2; // 0.30000000000000004
```

`number` ของ JavaScript คือ **IEEE 754 double** — เก็บเลขฐานสอง 0.1 ในฐานสองเป็นทศนิยมไม่รู้จบ
(เหมือน 1/3 = 0.333… ในฐานสิบ) จึงถูกปัดตั้งแต่ตอนเก็บ ความคลาดเล็กมาก แต่ **บวกสะสม** หลายร้อยรายการ
ยอดรวมจะคลาดทีละสตางค์ และการเทียบ `===` จะผิดทันที

### 1.2 ทางแก้: เก็บเป็น "หน่วยย่อย" (minor unit)

| เงิน       | เก็บเป็น `amountMinor` |
| ---------- | ---------------------- |
| ฿65        | `6500`                 |
| ฿125.50    | `12550`                |
| ¥500 (เยน) | `500` — เยนไม่มีทศนิยม |

จำนวนเต็มบวกลบกันได้แม่นยำเสมอ (ถึง `Number.MAX_SAFE_INTEGER` ≈ 9 พันล้านล้าน — พอสำหรับเงินบุคคล)
ทศนิยมเกิดขึ้น **ตอนแสดงผลเท่านั้น**

📁 `packages/contracts/src/payloads.ts` — `amountMinor: z.number().int()` · API ปฏิเสธ `65.5` ด้วย 422

### 1.3 แปลงข้อความ → หน่วยย่อย โดยไม่ผ่าน float

📁 `packages/core/src/money.ts` → `parseAmountToMinor`

```ts
// "1,250.75" → ต่อสตริง "1250" + "75" → Number("125075")
const minor = Number(whole + fraction.padEnd(digits, '0'));
```

⚠️ วิธีที่ดูง่ายกว่า `Math.round(parseFloat(text) * 100)` **ใช้ได้เกือบทุกกรณี** แต่ "เกือบ" คือปัญหา —
`1.005 * 100 = 100.49999999999999` → ปัดได้ 100 ไม่ใช่ 101 · การต่อสตริงไม่มีขั้นตอนไหนเป็น float เลย

ทศนิยมของแต่ละสกุลอ่านจาก `Intl.NumberFormat(…).resolvedOptions().maximumFractionDigits` —
ไม่ต้องดูแลตาราง "THB=2, JPY=0" เอง

### 1.4 แสดงผล

`formatMoney(842000, 'THB', { decimals: false })` → `฿8,420` (KPI) · `formatMoney(79900)` → `฿799.00` (ตาราง/บิล)
ตามสเปก 8.11.3 · ใช้ `Intl.NumberFormat('th-TH', { style: 'currency' })` ซึ่งรู้เองว่าสัญลักษณ์อยู่หน้า และใส่ลูกน้ำทุกสามหลัก

🎤 _"ทำไมไม่ใช้ `DECIMAL` ในฐานข้อมูล"_ → ใช้ได้ (Postgres `NUMERIC` แม่นยำ) แต่พอข้อมูลออกมาเป็น JSON
แล้วเข้า JavaScript ก็กลายเป็น `number` (float) อีก · เราเก็บใน JSONB ด้วย จึงเลือก integer ตลอดทาง
ทุกชั้นพูดภาษาเดียวกัน ไม่มีจุดไหนต้องแปลง

## 2. "เดือนนี้" เริ่มตอนไหน

### 2.1 ปัญหา

ฐานข้อมูลเก็บเวลาเป็น UTC (บท 13) แต่ "เดือนกันยายน" ของคนไทยเริ่ม **1 ก.ย. 00:00 เวลาไทย**
ซึ่งตรงกับ **31 ส.ค. 17:00 UTC** — ถ้า query ด้วย `>= '2026-09-01T00:00Z'`
รายจ่ายมื้อเช้าวันที่ 1 (ก่อน 07:00) จะหลุดไปอยู่เดือนสิงหาคม

### 2.2 ทางแก้: หาขอบเดือนจาก "หน้าปัด" ของผู้ใช้

📁 `packages/core/src/time.ts` → `monthBoundsInTimeZone` / `periodBounds`

```ts
start: zonedTimeToUtc(`${year}-${pad(month)}-01T00:00:00`, timeZone),
end:   zonedTimeToUtc(`${next.y}-${pad(next.m)}-01T00:00:00`, timeZone), // ต้นเดือนถัดไป (exclusive)
```

- ใช้ `[start, end)` แบบเดียวกับ "วันนี้" ในบท 13 — ต้นเดือนถัดไปเป็นขอบ **ไม่รวม** จึงไม่มีรายการไหนนับซ้ำสองเดือน
- **ไม่** คำนวณ `end = start + จำนวนวัน × 24 ชม.` — เดือนที่มี DST (มี.ค. ของ New York) ยาว 30 วัน 23 ชม.
  เทสต์ `periodBounds('2026-03', 'America/New_York')` จับเรื่องนี้ไว้
- `periodBounds(period, tz, shift)` เลื่อนเดือนด้วยเลขคณิต `ปี×12 + เดือน` — ข้ามปีได้โดยไม่มี if (ใช้ทำกราฟย้อนหลัง 6 เดือน)
- จำนวนวันในเดือน: `new Date(Date.UTC(year, month, 0)).getUTCDate()` — "วันที่ 0 ของเดือนถัดไป" คือวันสุดท้ายของเดือนนี้

## 3. โมดูลที่สอง — พิสูจน์ plugin architecture

### 3.1 สิ่งที่ต้องเขียน vs สิ่งที่ต้องแก้

| ไฟล์                                               | ทำอะไร                                            |
| -------------------------------------------------- | ------------------------------------------------- |
| 📁 `modules/expense/expense.trackable.ts` _(ใหม่)_ | implement `TrackableModule` + `@RegisterModule()` |
| 📁 `modules/expense/expense.module.ts` _(ใหม่)_    | NestJS module                                     |
| 📁 `app.module.ts` _(แก้ 2 บรรทัด)_                | import + ใส่ในรายการ                              |
| `entries/`, `core/registry/`, Today, Calendar      | **ไม่แตะเลย**                                     |

ทันทีที่ลงทะเบียน `POST /entries { module: 'expense' }` ใช้ได้ — เพราะ entries service ถาม registry ว่ามีโมดูลนี้ไหม
แล้วใช้ `payloadSchema` ของโมดูลนั้น validate (เทสต์ `expenses.int-spec.ts` พิสูจน์ข้อนี้)
ก่อนหน้านี้ `module: 'expense'` ได้ error "unknown module" ทั้งที่ schema มีอยู่ใน contracts แล้ว

### 3.2 กฎทางธุรกิจอยู่ในฟังก์ชันเดียว

"ใช้จ่ายจริง" นับอะไรบ้าง — ตัดสินที่ `isSpent()` ที่เดียว:

| รายการ                     | นับ? | เหตุผล                                           |
| -------------------------- | ---- | ------------------------------------------------ |
| รายจ่ายทั่วไป              | ✅   |                                                  |
| รายรับ                     | ❌   | คนละทิศ                                          |
| ยกเลิกแล้ว / ลบแล้ว        | ❌   |                                                  |
| บิลที่ยังไม่จ่าย (pending) | ❌   | ยังไม่ได้เสียเงิน — เป็น "ภาระ" ไม่ใช่ "รายจ่าย" |
| บิลที่จ่ายแล้ว (done)      | ✅   |                                                  |

ถ้าแต่ละหน้า (Today, Expenses, Weekly) เขียนเงื่อนไขนี้เอง วันหนึ่งตัวเลขสามหน้าจะไม่ตรงกัน

### 3.3 ปฏิทินขึ้นเฉพาะบิล

`toCalendarEvent` คืน `null` สำหรับรายจ่ายจร (สเปก 6.3) — กาแฟ 3 แก้วต่อวันบนปฏิทินคือสัญญาณรบกวน
สิ่งที่ควรเห็นในปฏิทินคือ "วันที่ต้องจ่าย" ไม่ใช่ "วันที่จ่ายไปแล้ว"

## 4. Parser แบบ rule-based: "กาแฟ 65"

### 4.1 ทำไมไม่ใช้ LLM

สเปก 6.4: ช้า (หลายร้อย ms), มีค่าใช้จ่ายต่อครั้ง, ผลไม่แน่นอน (เทสต์ยาก) — ข้อความสั้นแบบนี้มีโครงสร้างพอให้ regex จับได้
แต่ละโมดูลลอง parse เอง แล้วคืน `confidence` ให้ตัวกลาง (Phase 5) เลือกตัวที่มั่นใจที่สุด

### 4.2 โครงของ regex

📁 `apps/api/src/modules/expense/expense-text.ts`

```
^(?<title>.+?)  \s+  ฿?\s*(?<amount>ตัวเลข)  \s*(?<unit>บาท|฿|thb)?  (?:\s+(?<rest>.*))?$
 "กาแฟ"               "65"                        "บาท"                    "ทุกวันที่ 5"
```

- **named group** `(?<title>…)` อ่านง่ายกว่า `m[1]` และไม่พังเมื่อเพิ่มวงเล็บ
- `.+?` (lazy) — กินให้น้อยที่สุด ไม่งั้น `.+` จะกลืน "ค่าเน็ต 799 ทุกวันที่" แล้วเหลือแค่ "5" เป็นจำนวนเงิน
- ต้องมี **ช่องว่าง** หน้าตัวเลข → `ais5g` ไม่ถูกตีเป็นเงิน 5 บาท

### 4.3 กับดัก: substring ซ้อนกัน → "คำที่ยาวที่สุดชนะ"

```
"ค่าน้ำมัน"  มี  "ค่าน้ำ" (สาธารณูปโภค)  และ  "น้ำมัน" (เดินทาง)  อยู่ข้างใน
"หนังสือ"   มี  "หนัง" (บันเทิง)
```

ถ้าใช้ "เจอคำแรกในรายการ" ผลขึ้นกับลำดับที่เขียนพจนานุกรม — แก้ลำดับทีหนึ่ง อีกเคสพัง
`guessCategory` เลือก **keyword ที่ยาวที่สุด** ที่พบ แล้วใส่คำเต็ม "ค่าน้ำมัน" ไว้ในหมวดเดินทาง
→ กฎเดียว ไม่ขึ้นกับลำดับ (นี่คือหลัก longest match แบบเดียวกับที่ lexer ของภาษาโปรแกรมใช้: `>=` ต้องไม่ถูกอ่านเป็น `>` กับ `=`)

### 4.4 Table-driven test

```ts
const CASES = [
  { input: 'กาแฟ 65', title: 'กาแฟ', amountMinor: 6500, category: 'food' },
  { input: 'ค่าน้ำมัน 1,200', title: 'ค่าน้ำมัน', amountMinor: 120000, category: 'transport' },
  …
];
it.each(CASES)('"$input"', …);
```

เพิ่มเคสที่ผู้ใช้เจอจริง = เพิ่ม 1 บรรทัด · ชื่อเทสต์คือ input เอง เวลาล้มรู้ทันทีว่าประโยคไหน

### 4.5 วันครบกำหนดของ "ทุกวันที่ 31"

`nextDueDate(31, …)` ในเดือนที่มี 30 วัน → วันที่ 30 (clamp ไปวันสุดท้าย) ไม่ใช่ข้ามไปเดือนถัดไป
เหมือนที่ธนาคารตัดบัตรเครดิต · rrule เต็มรูปแบบมาใน Phase 3

## ข้อเสียที่ยอมรับ

- พจนานุกรมหมวดเขียนด้วยมือ — คำที่ไม่อยู่ในรายการได้ `other` (ผู้ใช้แก้ได้ใน UI) · Phase 8 อาจเรียนรู้จากที่ผู้ใช้แก้
- คำสั้นอย่าง `ยา`, `true` จับ substring ผิดได้ (`true` ใน "true wallet") — ยอมรับเพราะ confidence ยังต่ำ ผู้ใช้เห็น preview ก่อนบันทึก
- ยังไม่มี rrule — "ทุกวันที่ 5" ได้แค่ `isBill` + วันครบกำหนดครั้งถัดไป
