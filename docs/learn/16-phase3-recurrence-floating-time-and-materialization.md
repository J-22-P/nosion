## 1. RRULE — ภาษาสำหรับ "ทุก ๆ …"

### 1.1 ทำไมไม่คิดรูปแบบเอง

"ทุกวันจันทร์และพุธ" · "ทุก 2 สัปดาห์" · "วันศุกร์สุดท้ายของเดือน" · "ทุกปีวันที่ 29 ก.พ." —
ถ้าออกแบบ JSON เองจะไม่จบ RFC 5545 (iCalendar) มีภาษานี้อยู่แล้ว ใช้กันใน Google Calendar, Outlook, Apple Calendar
และมีไลบรารีทุกภาษา

### 1.2 อ่าน RRULE

```
FREQ=MONTHLY;BYMONTHDAY=31          ทุกเดือน วันที่ 31
FREQ=WEEKLY;INTERVAL=2;BYDAY=MO,WE  ทุก 2 สัปดาห์ วันจันทร์และพุธ
FREQ=MONTHLY;BYDAY=FR;BYSETPOS=-1   ศุกร์สุดท้ายของเดือน
```

- `FREQ` = ช่วงหลัก · `INTERVAL` = ทุกกี่ช่วง · `BY…` = กรอง/ขยายวันในช่วง
- `BYSETPOS` = "จากวันที่ได้ในช่วงนี้ เอาตัวที่ n" (`-1` = ตัวสุดท้าย) — จำตัวนี้ไว้ จะกลับมาในหัวข้อ 4

### 1.3 สิ่งที่เราไม่ยอมให้อยู่ในสตริง

📁 `packages/core/src/recurrence.ts` → `parseRecurrenceRule` ปฏิเสธ `DTSTART / UNTIL / COUNT / TZID / BYHOUR / BYMINUTE / BYSECOND`
และ `FREQ` ต่ำกว่ารายวัน

เหตุผล: ข้อมูลเดียวกันต้องมี **ที่เดียว** — วันเริ่มอยู่ใน `startsAt`, โซนใน `timezone`, จุดจบใน `endType`
ถ้ายอมให้มีทั้งในคอลัมน์และในสตริง วันหนึ่งสองที่จะไม่ตรงกัน แล้วต้องเดาว่าเชื่อตัวไหน

🎤 _"ทำไมไม่รองรับทุกชั่วโมง"_ → กฎรายชั่วโมง 90 วัน = 2,160 entry ต่อกฎ · ไม่มี use case ในแอป · เพิ่มทีหลังง่ายกว่าเอาออก

## 2. "ทุกวัน 9 โมง" ≠ ทุก 24 ชั่วโมง

ทบทวนจากบท 13: **instant** (จุดเวลาจริง, UTC) กับ **เวลาหน้าปัด** (ที่นาฬิกาบนผนังแสดง) ไม่ใช่สิ่งเดียวกัน

| วัน (New York) | หน้าปัด | offset | UTC   |
| -------------- | ------- | ------ | ----- |
| 7 มี.ค. 2027   | 09:00   | −05:00 | 14:00 |
| 15 มี.ค. 2027  | 09:00   | −04:00 | 13:00 |

กฎการเกิดซ้ำของคนพูดถึง **หน้าปัด** เสมอ ถ้าบวกทีละ 86,400 วินาที หลัง DST การนัดจะเลื่อนไปเป็น 10:00
ประเทศไทยไม่มี DST จึงไม่เห็นบั๊กนี้ — จนกว่าจะมีผู้ใช้คนแรกในยุโรป · เทสต์จึงต้องใช้ `America/New_York` แม้ผู้ใช้ส่วนใหญ่อยู่ไทย

## 3. Floating time — ให้ไลบรารีคิดในโลกที่ไม่มี DST

### 3.1 ปัญหาของ `tzid`

rrule.js มีตัวเลือก `tzid` แต่ทำงานโดยอาศัย `Intl` ของ runtime และมีบั๊กข้าม DST ที่รู้กันมานาน —
ผลบน Node กับในเบราว์เซอร์อาจต่างกัน เราต้องการ engine ที่ผลเหมือนกันทุกที่

### 3.2 วิธีของเรา

```
startsAt (UTC จริง)  ──toFloating──▶  "09:00" ใส่ในฟิลด์ UTC  ──rrule (tzid: null)──▶  ทุกรอบเป็น "…T09:00:00Z"
                                                                                          │
                                       slot UTC จริง (14:00 / 13:00)  ◀──fromFloating────┘
```

- **floating** = เวลาหน้าปัดที่ "ยังไม่ผูกโซน" — ยืมฟิลด์ UTC ของ `Date` มาเก็บ เพราะ UTC ไม่มี DST
- rrule คำนวณในโลกนี้ได้ถูกเสมอ: ทุกวัน 09:00 ก็คือ 09:00 ทุกวัน
- แปลงกลับ **ทีละรอบ** ด้วย `zonedTimeToUtc` — ฟังก์ชันเดียวกับที่ใช้ทั้งระบบ (บท 13) ถ้ามันถูก engine ก็ถูก

⚠️ `Date` แบบ floating **ห้ามหลุดออกนอกไฟล์** — ใครเอาไป `toISOString()` จะได้เวลาผิดโดยไม่รู้ตัว
ฟังก์ชัน public ทุกตัวรับและคืน UTC จริงเท่านั้น

### 3.3 ช่วงค้นหาต้องกว้างกว่าจริง

ผู้เรียกให้ขอบเป็น UTC แต่ rrule ค้นในเวลาหน้าปัด — offset ต่างกันได้ถึง ±14 ชม.
จึงขยายขอบ ±2 วัน แล้ว **กรองซ้ำด้วย UTC จริง** หลังแปลง (`occurrencesBetween`) ง่ายกว่าคำนวณขอบให้พอดี และไม่มีทางพลาดรอบที่ขอบ

### 3.4 เวลาที่ไม่มีอยู่จริง

คืนเข้า DST ของ New York นาฬิกากระโดด 01:59 → 03:00 · "ทุกวัน 02:30" วันนั้นไม่มี 02:30
นโยบาย: **เลื่อนไปเวลาที่มีจริง** (03:30) ไม่ทิ้งรอบ — บิลที่หายไปหนึ่งรอบแย่กว่าบิลที่มาช้าหนึ่งชั่วโมง

## 4. บิลวันที่ 31 ในเดือนกุมภาฯ — clamp

### 4.1 RFC บอกให้ข้าม

ตาม RFC 5545 `BYMONTHDAY=31` ใน ก.พ. **ไม่เกิด** — ถูกต้องตามมาตรฐาน แต่ผิดสำหรับคน:
ค่าเน็ตตัดวันสิ้นเดือนไม่ได้หายไปในเดือนกุมภาฯ นี่คือ DoD ของ Phase 3

### 4.2 แก้ด้วยภาษาเดียวกัน ไม่ใช่ด้วย if

```
BYMONTHDAY=31   ─▶   BYMONTHDAY=28,29,30,31;BYSETPOS=-1
```

อ่านว่า "จากวันที่ 28–31 ที่มีจริงในเดือนนี้ เอาวันสุดท้าย":

| เดือน   | วันที่มีจริงในชุด | ได้ |
| ------- | ----------------- | --- |
| ม.ค.    | 28, 29, 30, 31    | 31  |
| ก.พ.    | 28                | 28  |
| ก.พ. 28 | 28, 29            | 29  |
| เม.ย.   | 28, 29, 30        | 30  |

= `min(31, วันสุดท้ายของเดือน)` พอดี โดยไม่ต้องเขียนตรรกะปฏิทินเอง และ **COUNT ยังนับถูก** เพราะ rrule เห็นทุกรอบเป็นรอบปกติ
(ถ้าเติมวันที่หายเองหลัง rrule — "จ่าย 12 งวด" จะได้ 7 งวดจากวันที่ 31 แล้วเติมอีก 5 → ต้องนับเองซ้ำ)

📁 `applyMonthEndClamp` — ใช้กับ MONTHLY และ YEARLY ที่มีเดือนเดียว (29 ก.พ. → 28 ก.พ.)

### 4.3 เมื่อไรไม่ clamp

- กฎที่มี `BYDAY` / `BYSETPOS` อยู่แล้ว — "ศุกร์สุดท้าย" ไม่ใช่เรื่องวันที่
- กฎหลายวันต่อเดือน (`15,31`) — `BYSETPOS` เลือกได้แค่ตัวเดียวต่อเดือน จะทำให้วันที่ 15 หาย

ข้อเสียที่เกิดจากการเลือกนี้บันทึกไว้ใน ADR-010

🎤 _"ทำไมไม่ให้ผู้ใช้เลือก 'วันสุดท้ายของเดือน' (`-1`)"_ → ใช้ได้แค่คนที่เลือก 31 · คนเลือก 30 ยังหาย ก.พ. · และผู้ใช้ต้องรู้ปัญหาก่อนถึงจะเลือกถูก
UI จึงบอกแค่ใต้ช่องเมื่อเลือก 29–31 ว่า "เดือนที่ไม่มีวันนี้จะใช้วันสุดท้ายของเดือน"

## 5. Lazy materialization — สร้างล่วงหน้าแค่พอ

### 5.1 สามทางเลือก

| ทาง                                       | ปัญหา                                                                |
| ----------------------------------------- | -------------------------------------------------------------------- |
| คำนวณตอนอ่านทุกครั้ง (ไม่เก็บ)            | ทำเครื่องหมายเสร็จ/แก้จำนวนเงิน "รอบเดียว" ไม่ได้ — ไม่มี row ให้แก้ |
| สร้างทั้งหมดตอนตั้งกฎ                     | "ไม่มีวันสิ้นสุด" = อนันต์                                           |
| **สร้างล่วงหน้า 90 วัน แล้วเติมเรื่อย ๆ** | ต้องจำว่าสร้างถึงไหนแล้ว → `materializedUntil`                       |

### 5.2 ช่วงเปิดซ้าย `(after, until]`

`occurrencesBetween(spec, after, until)` ไม่รวมขอบซ้าย รวมขอบขวา — เรียกต่อกันได้ไม่ซ้ำไม่ขาด:

```
(null, d90]  →  เก็บ materializedUntil = d90
(d90, d91]   →  เก็บ d91 …
```

รูปแบบเดียวกับ cursor pagination (บท 06): "ขอของที่อยู่หลังตัวสุดท้ายที่เห็น"

### 5.3 ไม่สร้างย้อนหลัง

ตั้งบิลที่ `startsAt` เมื่อ 6 เดือนก่อน → เริ่มสร้างจาก "เมื่อวาน" ไม่ใช่ 6 รายการค้างจ่าย · สเปกไม่ได้ระบุ — เป็นการตัดสินใจเอง

## 6. Idempotency — cron รันซ้ำ รันพร้อมกัน ก็ไม่สร้างซ้ำ

cron อาจรันสองครั้ง (retry) หรือสองตัวพร้อมกัน (ผู้ใช้กดปุ่ม Materialize ตอน cron ทำงาน) — ต้องได้ผลเท่ากับรันครั้งเดียว

**ชั้นที่ 1 — ฐานข้อมูลเป็นคนตัดสิน:** unique `(recurrenceRuleId, recurrenceSlot)` + `createMany({ skipDuplicates: true })`
สองตัวแทรกรอบเดียวกัน ตัวหลังถูกข้ามเงียบ ๆ (`ON CONFLICT DO NOTHING`) — ไม่ต้องล็อก ไม่ต้องอ่านก่อนเขียน

**ชั้นที่ 2 — ค่าเดินหน้าเท่านั้น:**

```ts
updateMany({
  where: { id, materializedUntil: { lt: horizon } },
  data: { materializedUntil: horizon },
});
```

ตัวที่ช้ากว่าและถือค่าเก่าจะไม่ดึง `materializedUntil` ถอยหลัง (เทียบกับ optimistic concurrency ในบท 06 — เงื่อนไขอยู่ใน `WHERE`)

เทสต์บังคับในสเปก: **materialize 2 ครั้งติดกัน → จำนวน entry เท่าเดิม** และใน integration ยิง `Promise.all` สองตัวพร้อมกันด้วย

## 7. "เฉพาะครั้งนี้" vs "ทุกรอบ"

### 7.1 Exception = EXDATE

ลบรอบเดียว → เพิ่ม slot เข้า `exceptions` + soft delete entry นั้น · engine ข้าม slot ใน exceptions เสมอ จึงไม่ถูกสร้างกลับ
ผู้ใช้ระบุเป็น **วันที่ในปฏิทินของกฎ** (`DELETE …/occurrences/2027-02-28`) ไม่ใช่ timestamp — คนไม่รู้ว่ารอบนั้นคือ 17:00Z
`slotOnLocalDate` แปลงให้

**เลื่อนรอบเดียว** = แก้ entry ตรง ๆ + slot เดิมเข้า exceptions — เฉพาะเมื่อวันเวลาเปลี่ยนจริง (แก้ชื่อไม่แตะ)

### 7.2 แก้ทั้ง series ไม่แตะอดีต

- รอบที่ผ่านไปแล้ว ทำเสร็จแล้ว หรือถูกแก้เอง (`version > 1`) = **ประวัติของผู้ใช้** ไม่เปลี่ยน
- รอบอนาคตที่ยัง `pending` และ `version = 1` (ไม่มีใครแตะ) ลบจริงเพื่อคืน unique slot แล้วสร้างใหม่ตาม template ใหม่
- `scope` เป็น query string (`?scope=this|series`) เพราะ `DELETE` ไม่มี body และไม่ปนกับ payload ของ entry

### 7.3 ลำดับใน transaction

ตรวจ template (422) **ก่อน** เปิด transaction → ใน transaction: แก้ entry พร้อม version check → ลบรอบอนาคต → เขียน template
→ **หลัง commit** ค่อย materialize — ถ้าขั้นสุดท้ายพัง ข้อมูลไม่เสีย cron คืนนั้นเติมให้
หลักทั่วไป: ใส่ใน transaction เฉพาะสิ่งที่ต้อง "ถูกด้วยกันหรือไม่เกิดเลย" งานที่ทำซ้ำได้ไว้ข้างนอก

## 8. Cron บน serverless และ secret ที่ "ปิดเป็นค่าเริ่มต้น"

### 8.1 ไม่มี process ให้ตั้งเวลา

API บน Vercel เป็น Function — ไม่มี `setInterval` ที่อยู่ค้าง (เหตุผลเดียวกับ ADR-001)
Vercel Cron จึง **เรียก HTTP** เข้ามาตามตาราง: `vercel.json → crons: "0 3 * * *"` → `GET /api/v1/internal/cron/recurrence`
งานจริงอยู่ใน `materializeDue()` ซึ่ง worker ของ Phase 4 เรียกตัวเดียวกันได้ — ตัวกระตุ้นเปลี่ยน ตรรกะไม่เปลี่ยน

### 8.2 ใครก็เรียก URL ได้

Vercel ส่ง `Authorization: Bearer <CRON_SECRET>` มาด้วย เราเทียบด้วย `timingSafeEqual`
(`===` หยุดเทียบที่ตัวอักษรแรกที่ต่าง → เวลาตอบรั่วว่าเดาถูกกี่ตัว)

**ไม่ได้ตั้ง `CRON_SECRET` = endpoint ตอบ 404** — fail closed: ลืมตั้งค่าแล้วระบบ "ไม่ทำงาน" ดีกว่า "เปิดให้ทุกคน"
และ 404 ไม่บอกผู้สุ่มยิงว่ามี endpoint นี้อยู่ · ผลข้างเคียง: บน staging ต้องตั้ง secret เองก่อน cron จะทำงาน (ขั้น 7)

### 8.3 งานเป็นชุด และพังทีละตัว

ทำทีละ 200 rule ตาม id · ข้าม rule ที่ยังมีล่วงหน้า ≥ 60 วัน · rule หนึ่งพังถูก log แล้วไปต่อ
— Function มีเวลาจำกัด และกฎของผู้ใช้หนึ่งคนที่ข้อมูลเสียต้องไม่ทำให้บิลของทุกคนหยุด

## 9. UI ที่ไม่ต้องรู้ RFC 5545

### 9.1 Builder เป็นฟังก์ชันล้วน

📁 `apps/web/src/features/recurrence/builder.ts` — `RecurrenceDraft` (ภาษาคน) → `buildRrule()` → สตริง RRULE
component แค่แสดงและเปลี่ยน draft · ตรรกะทั้งหมดเทสต์ได้โดยไม่ render อะไร (เหมือนบท 12)

เทสต์ที่สำคัญที่สุดเชื่อมสองฝั่ง: rrule ที่ builder สร้างจากวันที่ 31 → **engine จริง** ได้ 31 ม.ค., 28 ก.พ., 31 มี.ค.

### 9.2 Preview คำนวณที่ server

ถ้าคำนวณในเบราว์เซอร์ ผลอาจต่างจากที่ cron สร้างจริง (โซน, runtime) และต้องโหลด rrule ~13 kB gzip ทุกหน้า
→ `POST /recurrence-rules/preview` ใช้ engine ตัวเดียวกับ materialize · "สิ่งที่เห็น = สิ่งที่จะได้"

### 9.3 Preview ที่ไม่โกหก

ระหว่าง debounce 300ms รายการบนจอยังเป็นของค่าเก่า โดยไม่มีอะไรบอก (บท 15 หัวข้อ 9.2 เจอแบบเดียวกัน)
→ `isOutdated = ค่าที่ debounce แล้ว !== ค่าปัจจุบัน || isPlaceholderData` แล้วทำให้รายการจาง

### 9.4 import ทั้งแพ็กเกจ = โหลดทั้งแพ็กเกจ

`@nosion/core` index เป็น CJS → bundler tree-shake ไม่ได้ → ทุกหน้าที่เรียก `formatMoney` ได้ rrule ติดไปด้วย
แก้ด้วย subpath export (`@nosion/core/money`, `/recurrence`) + กฎ lint ห้าม import index ฝั่ง web — First Load /expenses 189 → 173 kB
บทเรียน: วัดก่อนเชื่อ — ปัญหานี้ไม่มีเทสต์ไหนแดง

---

## ข้อเสียที่ยอมรับ

- `BYMONTHDAY` หลายค่าต่อเดือนไม่ถูก clamp (ADR-010) · UI ยังไม่มี "จันทร์แรกของเดือน" แม้ engine รองรับ
- กู้คืนรอบที่ลบแล้วไม่ดึง slot ออกจาก exceptions — preview ยังไม่แสดงวันนั้น
- ไม่มี "รอบนี้และรอบถัดไป" แบบ Google Calendar — `series` มีผลตั้งแต่ตอนนี้อยู่แล้ว การแยกเป็นสองกฎยังไม่จำเป็น
- ยังไม่มีหน้าจัดการกฎ (ดู/หยุด/ลบ) — API พร้อม · reminder ของรอบใหม่รอ Phase 4
- cron วันละครั้ง: กฎที่เพิ่งแก้แล้ว materialize หลัง commit พัง จะเห็นรอบใหม่ช้าสุด 24 ชม.

## แบบฝึกหัดท้ายบท

1. เขียน RRULE ของ "ทุก 3 เดือน วันที่ 15" และ "อังคารที่ 2 ของทุกเดือน" แล้วเช็กด้วย `parseRecurrenceRule` + `nextOccurrences`
2. ทำไม `parseRecurrenceRule('FREQ=DAILY;COUNT=5')` ถูกปฏิเสธ ทั้งที่เป็น RRULE ถูกต้อง — ควรส่ง 5 รอบไปทางไหน
3. รัน `nextOccurrences` ของ "ทุกวัน 09:00 `America/New_York`" เริ่ม 10 มี.ค. 2027 — ดูค่า UTC รอบก่อน/หลัง 14 มี.ค. ต่างกันกี่ชั่วโมง
4. ใน `buildRule` เปลี่ยน `tzid: null` เป็น `tzid: spec.timezone` (และไม่แปลง floating) แล้วรัน `recurrence.test.ts` — เคสไหนแดง
5. ทำไมฟังก์ชันที่คืน `Date` แบบ floating ห้ามเป็น export — ยกตัวอย่างบั๊กที่จะเกิด
6. คำนวณด้วยมือ: `BYMONTHDAY=28,29,30;BYSETPOS=-1` ในเดือน ก.พ. 2028 ได้วันไหน แล้วรันเทียบ
7. ลบเงื่อนไข `hasWeekday || hasSetPos` ใน `applyMonthEndClamp` — กฎ "ศุกร์สุดท้ายของเดือน" ผิดอย่างไร
8. กฎ `BYMONTHDAY=15,31` เดือน เม.ย. ได้กี่รอบ? ถ้าเราใส่ `BYSETPOS=-1` ให้มันด้วยจะได้กี่รอบ
9. ลบ `skipDuplicates` ใน `materialize()` แล้วรัน integration "materialize พร้อมกัน" — error อะไร มาจาก constraint ไหน
10. ลบ `lt: horizon` ออกจาก where ของ `materializedUntil` — วาด timeline ของ request สองตัวที่ทำให้ค่าถอยหลัง
11. ทำไม `occurrencesBetween` ใช้ `(after, until]` ไม่ใช่ `[after, until]` — ถ้าใช้แบบหลัง materialize ซ้ำจะเกิดอะไร (และใครช่วยไว้)
12. ลองเรียก `/api/v1/internal/cron/recurrence` บน staging ก่อนและหลังตั้ง `CRON_SECRET` — status ต่างกันอย่างไร ทำไมก่อนตั้งไม่ใช่ 401
13. แก้รอบ มี.ค. ของบิลเอง (version 2) แล้ว "แก้ทุกรอบ" — รอบ มี.ค. เป็นอย่างไร เปิดดูที่ไหนในโค้ดว่าทำไม
14. ใน `use-recurrence.ts` ตั้ง `isOutdated` เป็น `false` ตลอด แล้วพิมพ์เปลี่ยนวันเร็ว ๆ ในตัวสร้าง — เห็นอะไรบนจอ
15. import `formatMoney` จาก `@nosion/core` (index) ในหน้าเว็บ แล้วรัน lint และ `next build` — เทียบ First Load ของ /expenses
