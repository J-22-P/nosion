## 1. "แก้ core 0 บรรทัด" ต้องวัดได้

คำว่า "แทบไม่ต้องแก้" พิสูจน์ไม่ได้ — ต้องเป็นตัวเลขจาก git:

```bash
git diff --numstat <commit ก่อนเริ่ม Phase 6> -- apps/api/src/core packages/core/src   # → ว่าง
git diff --numstat <commit ก่อนเริ่ม Phase 6> -- apps/api/src/app.module.ts            # → 2 0
```

และต้องนิยามให้ชัดว่า "core" คืออะไร: `apps/api/src/core` (registry, parser service) + `packages/core` (domain, interface, NL parser)
· ส่วนที่ **ไม่ควรต้องรู้จักโมดูลใหม่** อย่าง `entries/` (Today), `calendar/`, `parse/` ก็ต้องเป็น 0 เหมือนกัน
(`today.module.ts` +5 ใน Phase นี้คือการเพิ่ม Weekly Review ซึ่งเป็นฟีเจอร์ใหม่ ไม่ใช่การรองรับนิสัย — แยกให้เห็นในตาราง)

🎤 _"ถ้า interface ขาดสิ่งที่โมดูลใหม่ต้องใช้ล่ะ"_ → เจอจริงหนึ่งครั้ง: ปฏิทินอยากให้นิสัยมีปุ่ม "progress" แต่ `CalendarAction` มีแค่
`complete` / `open` · ทางที่ไม่แก้ core คือใช้ `open` ลิงก์ไปหน้า `/habits` แทน — **การยอมรับข้อจำกัดของ interface** คือต้นทุนจริงของสถาปัตยกรรมแบบนี้

## 2. นิสัยคือกฎการเกิดซ้ำ

📁 `apps/api/src/modules/habit/`

```
"ดื่มน้ำ 8 แก้ว ทุกวัน" ─⌘K/parser─► RecurrenceRule { rrule: FREQ=DAILY, template: { module: habit, payload: { kind: count, targetValue: 8 } } }
                                         │ materialize (Phase 3)
                                         ▼
                         Entry(16 ต.ค.) currentValue 5 · Entry(17 ต.ค.) 0 · …
```

ได้ฟรี: การสร้างล่วงหน้า, หยุด/ลบ, การเตือน, ปฏิทินรวม, iCal, ⌘K · สิ่งที่โมดูลเขียนเองมีแค่สิ่งที่เป็นของนิสัยจริง ๆ
(การตีความข้อความ, การ์ด Today, streak, ปุ่ม +1)

**ทำครบ = `status: done` หรือ `currentValue ≥ targetValue`** — ปุ่ม "สำเร็จ" ในปฏิทินเรียก `/entries/:id/complete` ตัวกลาง
ซึ่งไม่รู้จัก `currentValue` · ถ้านิยามว่าครบเฉพาะ currentValue ปุ่มในปฏิทินจะทำงานไม่ได้กับนิสัย

⚠️ กับดัก: รอบแรกของนิสัยต้องเป็น **เที่ยงคืนตามโซนผู้ใช้** — ถ้าใช้ "ตอนนี้" (`new Date()`) กฎจะสร้างทุกรอบที่ 10:23 ทุกวัน
และ "นอนก่อน 23:45" ห้ามใช้ 23:45 เป็นเวลาของรอบ (นั่นคือ deadline ไม่ใช่เวลาที่เกิด)

## 3. streak ที่ยุติธรรม

📁 `habit-streak.ts` (pure)

| สถานการณ์                      | ผล               | เหตุผล                                               |
| ------------------------------ | ---------------- | ---------------------------------------------------- |
| วันนี้ยังไม่ทำ                 | ไม่ตัด           | วันยังไม่จบ — ตอน 9 โมงเช้าไม่ควรเห็น streak = 0     |
| ข้ามโดยตั้งใจ (`skipped`)      | ไม่นับ ไม่ตัด    | ป่วย/เดินทาง — ไม่ลงโทษการวางแผน                     |
| วันที่ไม่มีรอบ (นิสัยเฉพาะวัน) | ไม่ตัด           | นับบน "รอบ" ไม่ใช่วันในปฏิทิน                        |
| พลาด                           | ตัด              |                                                      |
| รายสัปดาห์ 3 ครั้ง             | นับสัปดาห์ที่ครบ | สัปดาห์นี้ยังไม่ครบ = ยังไม่ตัด (หลักเดียวกับวันนี้) |

🎤 _"ทำไม streak ไม่เก็บเป็นตัวเลขใน DB แล้ว +1 ทุกวัน"_ → ค่าที่ derive ได้จากประวัติ ถ้าเก็บซ้ำต้องดูแลให้ตรงกันทุกครั้งที่ผู้ใช้แก้ประวัติ
(ย้อนติ๊กเมื่อวาน, ลบรอบ, ข้าม) · คำนวณสดจากประวัติ 400 วัน = ถูกเสมอ ราคาแค่ query เดียว

## 4. +1 พร้อมกัน 8 ครั้ง

รุ่นแรก (optimistic concurrency แบบเดียวกับ `PATCH /entries`):

```
อ่านแถว (version 5, currentValue 3) → คำนวณ 4 ใน Node → UPDATE … WHERE version = 5
แพ้ (มีคนเขียนก่อน) → อ่านใหม่ → ลองใหม่ (สูงสุด 3 ครั้ง)
```

integration test ยิง 8 คำขอพร้อมกัน → **ได้ไม่ถึง 8** · ทุกคำขออ่าน version เดียวกัน มีแค่ตัวเดียวชนะต่อรอบ ตัวที่แพ้ 3 รอบติดคืน 409 แล้วค่าหาย

รุ่นที่ใช้ (ADR-013): ให้ Postgres คำนวณเอง

```sql
UPDATE entries SET payload = jsonb_set(payload, '{currentValue}', to_jsonb(GREATEST(0, (payload->>'currentValue')::numeric + 1))) …
```

ใต้ READ COMMITTED: คำสั่งที่สองรอ row lock ของคำสั่งแรก แล้ว **ประเมินนิพจน์ใน `SET` ใหม่กับแถวเวอร์ชันล่าสุด** (EvalPlanQual)
→ ไม่มีใครแพ้ ไม่ต้อง retry

⚠️ กับดัก: ถ้าคำนวณค่าใหม่ใน subquery (`FROM (SELECT … ) v`) ค่าจาก subquery **ไม่ถูกประเมินใหม่** — ต้องอ้างคอลัมน์ของแถวเป้าหมายใน `SET` ตรง ๆ

🎤 _"optimistic concurrency ผิดตรงไหน"_ → ไม่ผิด — เหมาะกับ "แก้ฟอร์มทั้งก้อน" ที่ต้องการให้คนช้ากว่ารู้ว่ามีคนแก้ก่อน (409 แล้ว merge)
แต่ +1 คือการกระทำที่ **สลับลำดับได้** (commutative) — ไม่มีอะไรให้ merge · เลือกกลไกตามความหมายของการกระทำ

## 5. Weekly Review ที่ไม่รู้จักโมดูล

📁 `apps/api/src/entries/review/` — โครงเดียวกับ Today: query เดียว → `summarizeWeek()` ของแต่ละโมดูล → `Promise.allSettled`
(ส่วนหนึ่งพังไม่ลากทั้งหน้า) · "ของสัปดาห์นี้" = เกิดในสัปดาห์ **หรือ** ทำเสร็จในสัปดาห์ (งานเก่าที่ปิดได้สัปดาห์นี้ก็นับ)

**สัปดาห์ ISO** (`iso-week.ts`): W1 = สัปดาห์ที่มีวันที่ 4 ม.ค. · 1 ม.ค. 2027 อยู่ใน **2026-W53** · ปีที่มี 52 สัปดาห์ไม่มี W53 → 422

⚠️ บั๊กที่ integration จับได้: กลางสัปดาห์ นิสัยได้ "ทำสำเร็จ 1/7" แทน 1/1 — รอบของพรุ่งนี้ถึงวันอาทิตย์ **ถูก materialize ไว้แล้ว**
จึงถูกนับเป็น "ยังไม่ทำ" · แก้ที่โมดูล (ไม่ใช่ที่ Review): นับเฉพาะรอบที่ถึงวันแล้ว — ความรู้ว่า "รอบล่วงหน้าไม่ใช่ความล้มเหลว" เป็นของนิสัย

## 6. โมดูลที่เปิด/ปิดได้

`UserSettings.enabledModules` (มีตั้งแต่ Phase 0) + `registry.all(enabled)` ในทุก aggregator → ปิดนิสัย = Today/ปฏิทิน/Review/⌘K ไม่ถามโมดูลนั้น
ข้อมูลไม่หาย · โมดูลใหม่ **ปิดเป็นค่าเริ่มต้น** สำหรับผู้ใช้เดิม (ไม่โผล่การ์ดใหม่ใส่หน้าคนที่ไม่ได้ขอ) — เปิดเองที่การ์ด "โมดูล" ในหน้าตั้งค่า

integration test ยืนยันทั้งสองทาง: ปิดอยู่ "ดื่มน้ำ 8 แก้ว ทุกวัน" ได้ **งาน** · เปิดแล้วได้ **นิสัย**

## 7. demo ที่มีประวัติ

นิสัยที่ไม่มีประวัติดูไม่มีชีวิต (streak 0 ทุกตัว) — demo สร้างกฎ + รอบย้อนหลัง 14 วันด้วยค่าที่ออกแบบให้เห็นทุกกรณี
(พลาดเมื่อ 5 วันก่อน → streak 4 · ครบทุกวัน → 15 · ข้ามโดยตั้งใจ · รายสัปดาห์) · ตั้ง `materializedUntil` = รอบสุดท้าย
เพื่อให้ cron สร้างต่อเหมือนกฎของผู้ใช้จริง · dataset ยังเป็น pure function (ไม่มีฟังก์ชันอยู่ในผลลัพธ์ — เทสต์ deterministic เทียบด้วย `toEqual`)

## แบบฝึกหัดท้ายบท

1. รัน `git diff --numstat` เทียบ commit ก่อน Phase 6 กับไดเรกทอรี `apps/api/src/entries` ทั้งก้อน — อธิบายทุกบรรทัดที่เปลี่ยนว่าเกี่ยวกับนิสัยหรือไม่
2. เพิ่มชนิด `progress` ใน `CalendarAction` แล้วนับว่าต้องแก้ core กี่บรรทัด และหน้าปฏิทินเว็บต้องรู้อะไรเพิ่ม — คุ้มไหม
3. เปลี่ยน `increment` กลับเป็นแบบอ่าน-คำนวณ-เขียน + version แล้วเพิ่ม retry เป็น 20 ครั้ง — integration ผ่านไหม และใน production ยังมีปัญหาอะไร
4. เขียน UPDATE แบบ subquery (`FROM (SELECT … ) v`) แล้วยิง 8 คำขอพร้อมกัน — ได้กี่ และทำไม
5. เพิ่มกติกา "ข้ามได้ไม่เกิน 1 ครั้งต่อสัปดาห์ ไม่งั้นนับเป็นพลาด" ใน `dailyStreak` พร้อมเทสต์ 3 เคส
6. หาว่า 2026, 2027, 2032 มีกี่สัปดาห์ ISO แล้วยืนยันด้วย `mondayOfIsoWeek`
7. ลบเงื่อนไข "รอบถึงวันนี้แล้ว" ใน `summarizeWeek` แล้วเปิด `/review` วันพุธ — ตัวเลขนิสัยเป็นเท่าไร
8. เปิดโมดูลนิสัยให้ผู้ใช้ทุกคนเป็นค่าเริ่มต้นด้วย migration — มีผลอะไรกับผู้ใช้เดิมที่ไม่เคยใช้นิสัย
