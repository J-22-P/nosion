# 20 · Phase 7 — Offline sync: outbox, idempotency, conflict ระดับ field และการเปิดแอปโดยไม่มีเน็ต

> DoD ของ Phase นี้สั้นมาก: **เปิดโหมดเครื่องบิน → ใช้แอปได้ปกติ → ปิดโหมด → ข้อมูลขึ้น server ครบ**
> แต่ "ครบ" ซ่อนคำถามไว้หลายข้อ: **(1) ส่งซ้ำแล้วไม่ทำซ้ำได้อย่างไร (2) สองเครื่องแก้รายการเดียวกัน ใครชนะ และตัดสินจากอะไร

> (5) UI บอกความจริงเรื่องการซิงก์อย่างไร (6) บั๊กสามตัวที่ทำให้ "ออฟไลน์ได้" กลายเป็น "จอค้าง" — และทำไมเทสต์จับได้**

## 1. ภาพรวม: สามชั้น

```
 ผู้ใช้กด ──► entriesApi.complete(id)
               │
               ▼  runOrQueue — ทางแยกเดียว
   ออนไลน์ + คิวว่าง ──► POST /entries/:id/complete (ทางเดิม)
   ออฟไลน์ / คิวมีของ / เน็ตหลุดกลางทาง
               │
               ▼
   outbox (IndexedDB)  [{ opId, at, op: 'complete', target: { id } }, …]
               │  online · กลับมาที่แท็บ · ทุก 30 วิ · Background Sync · ปุ่ม "ซิงก์เดี๋ยวนี้"
               ▼
   POST /sync/push  (ครั้งละ ≤ 100 ตามลำดับ) ──► EntriesService ตัวเดิม ──► ผลรายตัว
```

ไม่มีตรรกะของรายการซ้ำที่ `/sync/push` — ทุก operation เรียก `EntriesService` / `ParseService` ตัวเดียวกับ endpoint ปกติ
(validation, การเตือน, กฎการเกิดซ้ำ, event ทำงานเหมือนออนไลน์ทุกอย่าง) · สิ่งที่เพิ่มมีแค่ **idempotency** กับ **การตัดสิน conflict**

## 2. Idempotency: ส่งซ้ำได้ ผลเท่าเดิม

เน็ตมือถือหลุด "หลัง" server ทำเสร็จแต่ "ก่อน" คำตอบมาถึง — client ไม่มีทางรู้ว่าทำไปแล้วหรือยัง จึงต้องส่งซ้ำ
คำถามคือส่งซ้ำแล้วอะไรพัง:

| operation        | ส่งซ้ำโดยไม่มีกลไก        | กันด้วย                        |
| ---------------- | ------------------------- | ------------------------------ |
| สร้างรายการ      | ได้สองรายการ              | `clientId` (unique ต่อผู้ใช้)  |
| ติ๊กเสร็จ        | ไม่เป็นไร (idempotent)    | เสร็จแล้วตอบสำเร็จ             |
| **เลื่อนวัน**    | **เลื่อนสองวัน**          | `opId` + ตาราง `sync_ops`      |
| **parse กฎใหม่** | **กฎสองตัว บิลเด้งสองที** | `opId` (clientId กันแค่ entry) |

📁 `apps/api/src/sync/sync.service.ts` — `once()`: เจอ `(userId, opId)` ใน `sync_ops` แล้ว → คืนผลเดิม + `replayed: true` ·
ยังไม่เจอ → ทำ แล้วบันทึกผล · ส่งพร้อมกันสองทาง (แท็บ + Background Sync) ตัวที่สองชน unique (`P2002`) ก็ไม่เป็นไร

🎤 _"ทำไมไม่ใช้ Idempotency-Key header ทั้งคำขอ"_ → คำขอหนึ่งมีหลาย operation และ **ผลเป็นรายตัว** (ตัวที่ 3 ล้ม ตัวอื่นยังทำ)
ชุดที่ส่งซ้ำอาจไม่เหมือนชุดเดิม (มีของเข้าคิวเพิ่ม) — key ต้องอยู่ระดับ operation

⚠️ ช่องที่ยอมรับ: เขียนรายการแล้วค่อยบันทึก `sync_ops` (ไม่อยู่ใน transaction เดียว) — server ตายตรงกลาง = ส่งซ้ำแล้วทำซ้ำ · หน้าต่างแคบมาก

## 3. Conflict ระดับ field: ตัดสินจาก "ค่าก่อนแก้"

สองเครื่องแก้รายการเดียวกันระหว่างที่เครื่องหนึ่งออฟไลน์ · `version` บอกได้แค่ว่า "มีคนแก้" ไม่บอกว่า **แก้ช่องไหน**
server ไม่มีประวัติรายช่อง แต่ client รู้ค่าก่อนแก้ของตัวเองอยู่แล้ว → ส่งมาด้วย (`base`)

📁 `apps/api/src/sync/merge.ts` (pure)

| ค่าบน server ตอนนี้  | ตัดสิน                       | ตัวอย่าง                                        |
| -------------------- | ---------------------------- | ----------------------------------------------- |
| เท่ากับค่าของ client | ไม่ชน (แก้ตรงกัน)            | ติ๊กเสร็จจากสองเครื่อง                          |
| เท่ากับ `base`       | client ชนะ (ไม่มีใครแตะ)     | มือถือแก้ priority · โน้ตบุ๊กแก้ชื่อ → `merged` |
| อย่างอื่น            | **server ชนะ** + รายงาน diff | แก้ชื่อทั้งสองเครื่อง → `conflict`              |

payload เทียบ **ทีละ key** (แก้จำนวนเงินกับหมวดคนละเครื่องรวมกันได้) · `occurredAt` เทียบเป็นจุดเวลา (`+07:00` กับ `Z` เวลาเดียวกัน = เท่ากัน)
· ลบ vs แก้ → **ลบชนะ** (`deleted`) · ทั้งหมดตามตารางในสเปก 7.4

⚠️ กับดักฝั่ง client: `base` ต้องอ่าน **ก่อน** optimistic update ทับแคช — `useOptimisticEntryMutation` แก้แคชใน `onMutate` ซึ่งรัน **ก่อน** `mutationFn`
ถ้าอ่านใน `mutationFn` จะได้ค่าใหม่เป็น base → server เห็นว่า "มีคนแก้" ทุกครั้ง → conflict ปลอม · แก้ด้วย `beforeApply` เก็บไว้ใน WeakMap ผูกกับ vars

## 4. ทางแยกเดียว: ตัดสินที่ชั้น api ไม่ใช่ใน hook

📁 `apps/web/src/lib/sync/offline.ts` — `runOrQueue({ online, op, local })`

- **ออฟไลน์ หรือคิวยังมีของ** → เข้าคิว · "ติ๊กเสร็จ" ของงานที่สร้างตอนออฟไลน์ต้องถึง server **หลัง** การสร้าง — ห้ามแซงคิวแม้เน็ตกลับมาแล้ว
- ออนไลน์ → เรียก API ตรง · **เน็ตหลุดระหว่างเรียก** (fetch โยน `TypeError`) → เข้าคิวแทนการแจ้ง error
- server ตอบ error (`ApiError` เช่น 409/422) → โยนต่อตามเดิม — คิวไม่ได้ช่วยอะไร

เข้าคิวแล้วคืน **ภาพที่คาดไว้** (`EntryDto` จากแคช + การเปลี่ยน) → โค้ดผู้เรียกเดิมทั้งหมด (toast, ⌘Z, undo) ทำงานต่อได้
· รายการที่สร้างตอนออฟไลน์ใช้ id ชั่วคราว `local:<clientId>` → operation ถัดไปอ้างด้วย `{ clientId }` และ server แปลงให้

**`networkMode: 'always'`** — ค่าเริ่มต้นของ TanStack Query (`'online'`) **พัก mutation ไว้ในหน่วยความจำ** ตอนออฟไลน์ (`mutationFn` ไม่ถูกเรียก
รีเฟรชแล้วหาย) — ทางแยกของเราจึงไม่มีโอกาสทำงาน · query ยังเป็น `'online'`: ออฟไลน์ไม่ยิง ข้อมูลเดิมค้างบนจอ

📁 `sync-engine.ts` — ลบออกจากคิวเมื่อ **server ตอบผลแล้ว** เท่านั้น · เน็ตหลุด/5xx/401/408/429 = เก็บไว้ส่งชุดเดิม (opId เดิม) ·
4xx อื่น = ส่งซ้ำก็ถูกปฏิเสธแบบเดิม → ทิ้งแล้วรายงาน (ไม่งั้นคิวค้างตลอดไปและบังทุกอย่างข้างหลัง) · คิวแยกตามผู้ใช้

## 5. เปิดแอปตอนไม่มีเน็ต: สี่อย่างต้องมาจากในเครื่อง

| ต้องมี    | มาจาก                                                                                     |
| --------- | ----------------------------------------------------------------------------------------- |
| HTML      | service worker — หน้า network-first (เก็บทุกครั้งที่โหลดสำเร็จ) + เก็บทุกหน้าล่วงหน้า     |
| JS / CSS  | service worker — `/_next/static/*` cache-first (ชื่อไฟล์มี hash: เนื้อหาไม่เปลี่ยน)       |
| ข้อมูล    | แคชของ TanStack Query ที่ `dehydrate` ลง IndexedDB → `hydrate` ตอนเปิด                    |
| **ตัวตน** | โปรไฟล์ในแคช (`setOfflineUser`) — access token อยู่ใน memory เท่านั้น ออฟไลน์ขอใหม่ไม่ได้ |

**ทำไม SW ไม่แคช API** — SW ไม่มี access token (บท 04: token อยู่ใน memory ของหน้า) และแคช HTTP ไม่รู้ว่าข้อมูลไหนใหม่กว่า ·
แคชของ query รู้ `dataUpdatedAt` → `hydrate` ไม่ทับของสดที่โหลดเสร็จก่อนอ่านดิสก์

**session ออฟไลน์** — ขอ token ไม่ได้มีสองแบบที่ต้องแยกให้ออก: **เน็ตหลุด** (`TypeError`) → ใช้โปรไฟล์ในแคช ·
**ถูกปฏิเสธ** (401) → หมดสิทธิ์จริง ออกจากระบบ · เน็ตกลับมาคำขอแรกได้ 401 → api-client หมุน token จาก refresh cookie เอง (single-flight เดิมจากบท 04)

⚠️ กับดัก: แคชจากดิสก์มาถึง **ก่อน** ผลของรอบนี้ → effect เห็น "มีโปรไฟล์แต่ไม่มี token" แล้วออกจากระบบ · แก้: รอ `isFetching` จบก่อนตัดสิน

**ความเป็นส่วนตัว** — เดิม logout ไม่ล้างแคชในหน่วยความจำ (คนถัดไปเห็นข้อมูลเก่าแวบหนึ่ง) พอแคชลงดิสก์กลายเป็นเรื่องจริงจัง →
สถานะกลายเป็น "ไม่ได้ล็อกอิน" เมื่อไร ล้างทั้งหน่วยความจำและดิสก์ · คิว outbox ไม่ลบ (แยกตามผู้ใช้ รอเจ้าของกลับมา)

## 6. UI ที่บอกความจริง

📁 `features/sync/connection.ts` (pure) — เน็ต + คิว → สถานะเดียวที่ pill, sidebar, hero, การ์ด Outbox ใช้ร่วม (ข้อความไม่มีทางขัดกันเอง):
`● Online` · `● ออฟไลน์ · รอซิงก์ 3` · `● กำลังซิงก์…` · มีเน็ตแต่ส่งไม่ผ่าน = `ซิงก์ไม่สำเร็จ · รอซิงก์ n` (ไม่โกหกว่า online)

- งานที่สร้างตอนออฟไลน์ไม่อยู่ในแคช (ไม่เคยมาจาก server) → ประกอบจากคิวเอง (`pendingView`: create/parse ให้กำเนิด, update/complete/delete แก้ต่อตามลำดับ)
- จุดสีเทา + "รอซิงก์" บนแถวที่มี operation ค้าง — ทั้งที่เห็น (title) และที่ screen reader อ่าน (ชื่อของแถว)
- "Sync ล่าสุด" = ครั้งที่ส่งของถึง server จริง — คิวว่างไม่นับ ไม่งั้นเปิดแอปทีไรก็ "เมื่อสักครู่"
- conflict ไม่เงียบ: toast บอกช่องที่ชน → "ดูรายละเอียด" → ตาราง ค่าของคุณ (ขีดฆ่า) / ค่าที่ใช้

## 7. บั๊กสามตัว: "ออฟไลน์ได้" ที่จริง ๆ คือ "จอค้าง"

ทั้งสามตัวผ่าน unit test ได้สบาย — เจอเพราะ E2E ในเบราว์เซอร์จริงที่ตัดเน็ตแล้ว **รีเฟรช**

1. **SW ติดตั้งไม่จบ** — regex หาไฟล์ใน HTML เก็บชิ้นส่วน URL ที่ถูกตัด (ได้ 404) และไม่ได้อ่าน body ของคำตอบที่ไม่ใช้ทิ้ง →
   HTTP/1.1 ได้ 6 connection ต่อ host · ค้างครบ 6 → fetch ตัวถัดไปรอไม่จบ → `install` ไม่จบ → SW ไม่เคยคุมหน้า ·
   แก้: รับเฉพาะ URL ที่จบด้วยนามสกุลไฟล์ (และ **ห้ามตัดที่วงเล็บ** — `chunks/app/(app)/tasks/page-….js`) + `res.body.cancel()` ทุกครั้งที่ไม่ใช้
2. **precache แย่งเน็ตกับหน้าแรก** — 10 หน้า + ~50 ไฟล์ทันทีที่ติดตั้ง · ย้ายไปทำเมื่อหน้าเว็บสั่ง (3 วิหลังเปิด) — ติดตั้งเสร็จทันที
3. **`indexedDB.open` ค้างเงียบได้** (ไม่ success ไม่ error — Safari รอบแรก, ดิสก์ใกล้เต็ม) → `whenRestored` ไม่จบ → session รอ → skeleton ตลอดไป ·
   แก้: เปิดได้ไม่เกิน 2 วิ (outbox ถอยไปหน่วยความจำ) · อ่านแคชได้ไม่เกิน 1.5 วิ (เกิน = เปิดแอปแบบไม่มีแคช)

บทเรียน: **ทุกการรอที่ไม่มีเวลาจำกัด คือจอค้างที่รอวันเกิด** · และ "ทำงานได้บนเครื่องผม" ของ SW ต้องทดสอบด้วยการรีเฟรชตอนออฟไลน์เท่านั้น

## ข้อเสียที่ยอมรับ

- ปุ่ม +1 ของนิสัย, bulk, จับเวลา ยังต้องออนไลน์ (+1 เป็น atomic ฝั่ง server — ต้องมี operation `increment` ใหม่)
- `parse` ตอนออฟไลน์ให้ server parse ตอนซิงก์ — "พรุ่งนี้" ที่พิมพ์ 23:59 แล้วซิงก์หลังเที่ยงคืนเลื่อนไปหนึ่งวัน
- Background Sync ปลุกได้แค่แท็บที่เปิดอยู่ (การส่งต้องใช้ token ในหน้า) · ไฟล์ static รุ่นเก่าสะสมในแคชจนกว่าจะเปลี่ยน `VERSION`
- งานออฟไลน์แสดงเฉพาะมุมมองที่ไม่กรองด้วยโปรเจกต์/แท็ก/คำค้น · conflict เก็บแค่ในหน่วยความจำ

## แบบฝึกหัดท้ายบท

1. ลบ `sync_ops` ออก (ใช้แค่ clientId) แล้วเขียน integration test ที่พิสูจน์ว่าเลื่อนวันส่งซ้ำแล้วเลื่อนสองครั้ง
2. ใน `merge.ts` ถ้า client ไม่ส่ง `base` เลย ผลของตาราง 3 ช่องเปลี่ยนเป็นอะไร — ทำไมเราเลือก "client ชนะ" กรณีไม่มี base
3. สลับลำดับใน `useOptimisticEntryMutation` ให้อ่าน base ใน `mutationFn` แล้วรัน E2E conflict — เห็นอะไร
4. เปลี่ยน `networkMode` ของ mutation กลับเป็นค่าเริ่มต้น แล้วรัน E2E ออฟไลน์ — เทสต์ไหนล้ม และทำไม
5. ทำให้ precache ไม่อ่าน body ของ 404 อีกครั้ง แล้วเปิด DevTools › Application › Service Workers — ค้างที่สถานะไหน
6. ออกแบบ operation `increment` สำหรับนิสัย: merge กับ +1 จากอีกเครื่องอย่างไรให้ได้ผลรวม (ใบ้: การบวกสลับลำดับได้)
7. ส่ง `now` ของ client ไปกับ operation `parse` — ต้องแก้ parser ฝั่ง server ตรงไหน และมีความเสี่ยงอะไรถ้านาฬิกาเครื่องผิด
8. หา `IndexedDB` ใน DevTools ของแอปแล้วอธิบายว่า `nosion-sync` กับ `nosion-cache` เก็บอะไร และอะไรหายเมื่อออกจากระบบ
