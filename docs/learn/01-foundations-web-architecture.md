# 01 · พื้นฐานสถาปัตยกรรมเว็บ (อ่านก่อนทุกอย่าง)

> ไฟล์นี้ไม่พูดถึงโค้ดของ NOSION เลย แต่เป็นคำศัพท์และภาพรวมที่ทุกไฟล์ถัดไปใช้อ้างอิง
> ถ้าคุณรู้เรื่องพวกนี้แล้ว ข้ามไป [02](./02-phase0-monorepo-and-tooling.md) ได้

## 1. โปรแกรมหนึ่งตัว = หนึ่ง process

เวลาเรารัน `node server.js` ระบบปฏิบัติการจะสร้าง **process** ขึ้นมาหนึ่งตัว
process คือโปรแกรมที่กำลังทำงานอยู่ มีหน่วยความจำเป็นของตัวเอง
และ **ตัวแปรใน process หนึ่งไม่มีทางถูกอ่านโดยอีก process หนึ่งได้โดยตรง**

นี่คือข้อเท็จจริงที่อธิบายเกือบทุกการตัดสินใจในระบบกระจาย:

- ถ้า API รัน 3 ตัวเพื่อรับโหลด (scale out) ตัวแปรใน memory ของแต่ละตัวจะไม่ตรงกัน
- เพราะฉะนั้นอะไรที่ต้อง "ใช้ร่วมกัน" ต้องไปอยู่นอก process → ฐานข้อมูล หรือ Redis
- ⚠️ นี่คือเหตุผลที่เราเก็บ session ใน PostgreSQL และเก็บ rate limit counter ใน Redis
  แทนที่จะเก็บใน `Map` ธรรมดาในโค้ด

**พอร์ต (port)** คือหมายเลขช่องทางที่ process จองไว้รับการเชื่อมต่อ
`localhost:3000` คือ "เครื่องนี้ ช่องที่ 3000" หนึ่งพอร์ตมีได้หนึ่ง process ในเวลาเดียวกัน
NOSION ใช้ 3000 (web), 3001 (api), 5432 (postgres), 6379 (redis)

## 2. Client / Server และ HTTP

**Server** = โปรแกรมที่รอรับคำขอ · **Client** = โปรแกรมที่ส่งคำขอ
เบราว์เซอร์เป็น client แต่ `web` (Next.js) เป็นได้ทั้งสองอย่าง: เป็น server ให้เบราว์เซอร์
และเป็น client เวลาเรียก `api`

**HTTP** คือรูปแบบข้อความที่ตกลงกันไว้ หนึ่งรอบสนทนามี 2 ส่วน:

```
คำขอ (request)                        คำตอบ (response)
POST /api/v1/entries HTTP/1.1         HTTP/1.1 201 Created
Host: localhost:3001                  Content-Type: application/json
Authorization: Bearer eyJhb...        x-request-id: 01J8XK2P9A
Content-Type: application/json
                                      {"id":"clx...","title":"ซื้อของ"}
{"module":"task","title":"ซื้อของ"}
```

องค์ประกอบที่ต้องรู้จัก:

| ส่วน            | คืออะไร              | ตัวอย่างในโปรเจกต์นี้                                                   |
| --------------- | -------------------- | ----------------------------------------------------------------------- |
| **Method**      | กริยา บอกว่าจะทำอะไร | `GET` อ่าน · `POST` สร้าง · `PATCH` แก้บางส่วน · `DELETE` ลบ            |
| **Path**        | ที่อยู่ของทรัพยากร   | `/api/v1/entries/clx123/complete`                                       |
| **Header**      | ข้อมูลกำกับ          | `Authorization`, `Content-Type`, `Cookie`                               |
| **Body**        | เนื้อข้อมูล (JSON)   | `{"title":"..."}`                                                       |
| **Status code** | ผลลัพธ์เป็นตัวเลข    | 200 สำเร็จ · 401 ไม่ได้ล็อกอิน · 404 ไม่เจอ · 409 ชนกัน · 422 ข้อมูลผิด |

**HTTP เป็น stateless** แปลว่าเซิร์ฟเวอร์ไม่จำอะไรจากคำขอก่อนหน้าเลย
ทุกคำขอต้องพกหลักฐานว่า "ฉันคือใคร" มาเอง — นี่คือจุดเริ่มของเรื่อง token ทั้งหมดใน [04](./04-phase1-auth-deep-dive.md)

**JSON** คือรูปแบบข้อความสำหรับส่งข้อมูลที่ทั้งสองฝั่งอ่านออก
มีแค่ string, number, boolean, null, array, object — **ไม่มีชนิด "วันที่"**
จึงต้องส่งวันที่เป็น string รูปแบบ ISO 8601 (`"2026-09-18T03:00:00.000Z"`) เสมอ
⚠️ `Z` ท้ายสุดแปลว่า UTC — เรื่องนี้สำคัญมากใน [03](./03-phase0-database-and-prisma.md)

## 3. REST คืออะไร (และไม่ใช่อะไร)

REST คือ **แนวทางการออกแบบ URL และการใช้ method ให้สม่ำเสมอ** โดยมองทุกอย่างเป็น
"ทรัพยากร" (resource) ที่มีที่อยู่ของตัวเอง

```
GET    /entries          → อ่านรายการทั้งหมด
POST   /entries          → สร้างใหม่
GET    /entries/:id      → อ่านตัวเดียว
PATCH  /entries/:id      → แก้บางส่วน
DELETE /entries/:id      → ลบ
```

REST ไม่ใช่ library ไม่ใช่ protocol — เป็นแค่ข้อตกลง ประโยชน์คือเมื่อคนอื่นเห็น URL
เขาเดาได้ทันทีว่าทำอะไร โดยไม่ต้องอ่านเอกสาร

ทางเลือกอื่นคือ **GraphQL** (client ระบุเองว่าอยากได้ field ไหน) และ **RPC/tRPC**
(เรียกเหมือนเรียกฟังก์ชัน) NOSION เลือก REST เพราะ over-fetching ไม่ใช่ปัญหาในสเกลนี้
และ REST อธิบายง่ายที่สุดในห้องสัมภาษณ์

## 4. ทำไมไม่รวมเป็นโปรแกรมเดียว

คำถามที่ควรตอบได้: "Next.js ก็เขียน API ได้ ทำไมต้องมี NestJS แยก?"

คำตอบไม่ใช่ "เพราะมันดูโปร" แต่เป็นข้อจำกัดทางเทคนิคที่จับต้องได้:

**Serverless function** (รูปแบบที่ Next.js API Routes รันบน Vercel) มีวงจรชีวิตแบบนี้:

```
มี request เข้ามา → ปลุก function → ทำงาน → ตอบกลับ → ดับ
```

function ไม่มีชีวิตอยู่ระหว่างคำขอ แปลว่า:

- ตั้งเวลา `setInterval` ไม่ได้ เพราะดับไปแล้ว
- เปิด connection ค้างไว้รอ job จากคิวไม่ได้
- ทำ in-memory cache ที่อยู่ข้ามคำขอไม่ได้

แต่หัวใจของ NOSION คือ **Reminder Engine** ที่ต้องยิงแจ้งเตือนตรงเวลาแม้ไม่มีใครเปิดเว็บ
ซึ่งต้องมี process ที่รันค้างตลอด → จึงต้องมี `worker` แยก และเมื่อมี worker แล้ว
การมี API เป็น long-running server ด้วยก็เป็นทางเลือกที่สอดคล้องกัน

🎤 **คำถามสัมภาษณ์:** "ทำไมแยก service?" — ตอบด้วยข้อจำกัดของ runtime ไม่ใช่รสนิยม
(เหตุผลเต็มอยู่ใน 📁 `docs/adr/001-separate-nestjs-from-nextjs.md`)

## 5. หน้าที่ของแต่ละแอปใน NOSION

### `apps/web` — Next.js

สร้าง HTML ส่งให้เบราว์เซอร์ และจัดการการโต้ตอบกับผู้ใช้
**ไม่มีสิทธิ์แตะฐานข้อมูลโดยตรง** ทุกอย่างต้องผ่าน API
เหตุผล: โค้ดฝั่ง frontend ถูกส่งไปรันในเครื่องผู้ใช้ ใครก็แก้ได้ จึงเชื่อถือไม่ได้

> **กฎเหล็กของความปลอดภัย:** การตรวจสอบใด ๆ ที่ทำแค่ฝั่ง frontend เท่ากับไม่ได้ตรวจ
> frontend validate เพื่อ **ประสบการณ์ที่ดี** (บอกผู้ใช้ทันทีว่าพิมพ์ผิด)
> backend validate เพื่อ **ความถูกต้อง** — ต้องทำทั้งคู่เสมอ

### `apps/api` — NestJS

เจ้าของกฎธุรกิจทั้งหมด ตรวจสิทธิ์ ตรวจข้อมูล อ่าน/เขียนฐานข้อมูล
ใครก็ตามที่อยากเปลี่ยนข้อมูลต้องผ่านด่านนี้

### `apps/worker` — BullMQ

ทำงานที่ "ไม่มีใครรอคำตอบ": ส่งอีเมล ยิง notification ล้างข้อมูลเก่า สรุปรายสัปดาห์
งานพวกนี้ต้องไม่ทำใน request เพราะจะทำให้ผู้ใช้รอนาน และถ้าพังจะพาคำขอพังไปด้วย

## 6. ฐานข้อมูล 2 ชนิด ทำไมต้องมีทั้งคู่

|                      | PostgreSQL                  | Redis                                                   |
| -------------------- | --------------------------- | ------------------------------------------------------- |
| เก็บที่ไหน           | ดิสก์ (ข้อมูลอยู่ถาวร)      | RAM เป็นหลัก                                            |
| เร็วแค่ไหน           | มิลลิวินาที                 | ไมโครวินาที                                             |
| ข้อมูลหายไหมถ้าดับ   | ไม่หาย                      | อาจหายได้ (ยอมรับได้)                                   |
| ใช้เก็บอะไรใน NOSION | ผู้ใช้ งาน โปรเจกต์ session | ตัวนับ rate limit, คิวงาน, รายการ session ที่ถูกเพิกถอน |

หลักคิด: **ข้อมูลที่หายไม่ได้ → PostgreSQL · ข้อมูลที่หายแล้วสร้างใหม่ได้ + ต้องเร็วมาก → Redis**

ตัวอย่างจริงในโปรเจกต์: ตัวนับ rate limit อยู่ใน Redis ถ้า Redis ล่ม เราเลือก
"ปล่อยผ่าน" (fail-open) เพราะการที่ทั้งระบบล็อกอินไม่ได้เลย แย่กว่าการที่มีคนยิงถี่ได้ชั่วคราว
📁 `apps/api/src/auth/guards/rate-limit.guard.ts`

## 7. คำที่จะเจอบ่อยและความหมายสั้น ๆ

- **API** — ช่องทางให้โปรแกรมคุยกับโปรแกรม (ในที่นี้คือ HTTP + JSON)
- **Endpoint** — หนึ่ง method + หนึ่ง path เช่น `POST /auth/login`
- **Payload** — เนื้อข้อมูลที่ส่งไป/กลับ
- **Middleware** — โค้ดที่ทำงาน "ระหว่างทาง" ก่อนถึงปลายทาง เช่น แปะ traceId ให้ทุกคำขอ
- **Environment variable (env)** — ค่าที่เปลี่ยนตามสภาพแวดล้อม (dev/prod) เช่น รหัสฐานข้อมูล
  ห้ามฝังลงโค้ด เพราะโค้ดขึ้น git แต่ความลับต้องไม่ขึ้น 📁 `.env.example`
- **Idempotent** — ทำซ้ำกี่ครั้งผลลัพธ์เหมือนเดิม (`DELETE` ควร idempotent, `POST` ปกติไม่)
- **Race condition** — สองอย่างเกิดพร้อมกันแล้วผลลัพธ์ขึ้นกับว่าใครถึงก่อน ซึ่งไม่แน่นอน
- **Graceful shutdown** — ปิดโปรแกรมโดยทำงานที่ค้างให้จบก่อน ไม่ตัดกลางคัน

## สรุปสิ่งที่ต้องติดตัวไปไฟล์ถัดไป

1. process แยกกัน = memory ไม่แชร์กัน → อะไรที่ต้องแชร์ต้องออกไปอยู่นอก process
2. HTTP stateless → ทุกคำขอต้องพกหลักฐานตัวตนมาเอง
3. frontend เชื่อถือไม่ได้ → ตรวจซ้ำที่ backend เสมอ
4. serverless รันงานค้างไม่ได้ → จึงต้องมี worker แยก
