# ADR-016: เข้าสู่ระบบด้วย Google / GitHub — Authorization Code + PKCE เขียนเอง · state ในคุกกี้เข้ารหัส · ผูกบัญชีเมื่ออีเมลยืนยันทั้งสองฝั่ง

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-17

## บริบท

เจ้าของต้องการให้ล็อกอินด้วย Gmail (Google) และ GitHub ได้ — GitHub ยังเป็นทางไปสู่การดึงงานลงปฏิทิน (ADR-017) ·
ระบบ session เดิมเขียนเอง (refresh rotation + reuse detection · ADR-005) และต้องคงไว้ · API รันบน Vercel Function (ไม่มี memory ร่วมระหว่างคำขอ) ·
เว็บเรียก API ผ่าน proxy โดเมนเดียวกัน · refresh cookie เป็น `SameSite=Strict`

## การตัดสินใจ

1. **เขียน flow เอง (~300 บรรทัด)** ไม่ใช้ Passport/Auth.js — ออก session ผ่าน `AuthService` ตัวเดิม (rotation · reuse detection · อีเมลเตือนครบ)
2. **PKCE (S256) ทั้งสองเจ้า** + `state` สุ่ม · ทั้งคู่เก็บใน**คุกกี้ที่เข้ารหัส AES-256-GCM** (`aad = "oauth-state"`) อายุ 10 นาที ใช้ครั้งเดียว ·
   คุกกี้นี้ `SameSite=Lax` (callback มาจากโดเมนผู้ให้บริการ = cross-site) · path `/api/v1/auth/oauth`
3. **จับคู่บัญชี:** เคยผูก → คนเดิม · อีเมลตรงกับผู้ใช้เดิม → ผูกอัตโนมัติ**เฉพาะเมื่อทั้งผู้ให้บริการและบัญชีเดิมยืนยันอีเมลแล้ว** ·
   บัญชีเดิมยังไม่ยืนยัน → ปฏิเสธ (`email_conflict`) · ไม่มี → สร้างใหม่ (ไม่มีรหัสผ่าน)
4. **สำเร็จ = ตั้ง refresh cookie แล้ว redirect** — ไม่ส่ง access token ทาง URL · เว็บขอ token เองตาม flow เดิม
5. **ผูกจากหน้าตั้งค่า** = `POST /auth/oauth/:provider/link` ได้ link intent (เข้ารหัส อายุ 2 นาที) แล้วเปิดหน้า — การเปิดหน้าไม่มี access token ติดไป
6. **scope น้อยที่สุด:** Google `openid email profile` · GitHub `read:user user:email` · repo ส่วนตัวขอ `repo` เพิ่มเมื่อผู้ใช้ติ๊กเอง
7. **เก็บ token เฉพาะ GitHub** (ต้องใช้ดึง issue) เข้ารหัสโดยผูก `aad` กับ id ของแถว · Google ใช้แค่ยืนยันตัวตน ไม่เก็บ

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                  | เหตุผลที่ไม่เลือก                                                                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Auth.js / NextAuth                        | มี session ของตัวเอง (ซ้อนกับ ADR-005) · ผูกกับ Next.js แต่ auth อยู่ที่ NestJS (ADR-001)                               |
| Passport strategies                       | ซ่อน PKCE/state ไว้ข้างใน · strategy ของ GitHub ยังไม่รองรับ PKCE ตรง ๆ · ต้องใช้ session store                         |
| เก็บ state ใน Redis                       | Redis ล่ม = ล็อกอินไม่ได้ทั้งระบบ · ยังต้องผูกกับเบราว์เซอร์ด้วยคุกกี้อยู่ดี (กัน login CSRF)                           |
| ผูกอัตโนมัติทุกครั้งที่อีเมลตรงกัน        | ช่องยึดบัญชีคลาสสิก: ผู้ร้ายสมัครด้วยอีเมลเหยื่อ (ยังไม่ยืนยัน) รอเหยื่อล็อกอินด้วย Google แล้วใช้รหัสผ่านของตัวเองเข้า |
| ส่ง access token ใน fragment ของ redirect | ค้างใน history/log ของเบราว์เซอร์ · ไม่จำเป็นเพราะ refresh cookie ทำงานอยู่แล้ว                                         |
| GitHub App แทน OAuth App                  | สิทธิ์อ่าน repo แบบละเอียดได้ แต่ผู้ใช้ต้องติดตั้ง App ทีละ org/repo · ตั้งค่าซับซ้อนกว่ามากสำหรับ portfolio            |

## ผลที่ตามมา

**ได้:** ไม่มี dependency ใหม่ · ทุกขั้นมี integration test (ปลอมที่ `fetch` ชั้นนอกสุด ข้างในวิ่งจริง) · ไม่ต้องพึ่ง Redis ·
ผู้ใช้ที่สมัครด้วย OAuth ตั้งรหัสผ่านทีหลังได้ผ่าน "ลืมรหัสผ่าน" · กันการยกเลิกทางเข้าระบบทางสุดท้าย

**เสีย:** OAuth App ของ GitHub ไม่มี scope "อ่านอย่างเดียว" สำหรับ repo ส่วนตัว (`repo` = เขียนได้ด้วย — ยอมรับและบอกผู้ใช้ตรง ๆ) ·
เปลี่ยน `ENCRYPTION_KEY` = token ที่เก็บไว้ถอดไม่ได้ (ต้องเชื่อม GitHub ใหม่) · callback URL ผูกกับโดเมน (`API_URL`) ต้องลงทะเบียนแยกทุกสภาพแวดล้อม ·
ยังไม่ได้ลองกับ Google/GitHub ตัวจริงจนกว่าเจ้าของจะสร้าง OAuth app
