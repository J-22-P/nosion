# ADR-010: คำนวณการเกิดซ้ำใน "floating time" และ clamp วันสิ้นเดือน

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-15

## บริบท

Recurrence Engine (สเปก 6.1) ต้องตอบว่ากฎหนึ่ง "เกิดเวลา UTC ไหนบ้าง" ให้ถูกในสองเรื่องที่ไลบรารีมักทำผิด

1. **โซนเวลา + DST** — "ทุกวัน 09:00 New York" ต้องได้ 14:00 UTC ในฤดูหนาว และ 13:00 UTC ในฤดูร้อน
   ตัวเลือก `tzid` ของ rrule.js อาศัย `Intl` ของ runtime และมีบั๊กข้าม DST ที่เปิดค้างมานาน ผลจึงขึ้นกับเครื่องที่รัน
2. **วันที่ไม่มีในเดือน** — RFC 5545 กำหนดให้ `BYMONTHDAY=31` **ข้าม** เดือนที่ไม่มีวันที่ 31
   บิลค่าเน็ต "ทุกวันที่ 31" จะหายไป 5 เดือนต่อปีโดยไม่มีใครรู้ — ขัดกับ DoD ของ Phase 3 โดยตรง

## การตัดสินใจ

**1. คำนวณใน floating time แล้วแปลงเป็น UTC ทีละรอบ** (📁 `packages/core/src/recurrence.ts`)

- `toFloating(startsAt, tz)` — ย้าย "เวลาหน้าปัด" ในโซนของกฎมาใส่ฟิลด์ UTC ของ `Date` (09:00 New York → `…T09:00:00Z`)
- ให้ rrule.js คำนวณบน `Date` แบบนี้ด้วย `tzid: null` — ในโลกของ UTC ไม่มี DST rrule จึงไม่มีโอกาสผิด
- `fromFloating(slot, tz)` — แปลงแต่ละรอบกลับเป็นเวลาจริงด้วย `zonedTimeToUtc` ตัวเดียวกับที่ใช้ทั้งระบบ
- เวลาหน้าปัดที่ไม่มีจริงตอนเข้า DST (02:30) เลื่อนไปเวลาที่มีจริง ไม่ทิ้งทั้งรอบ
- ขอบช่วงค้นหาขยาย ±2 วันในเวลาหน้าปัด แล้วกรองซ้ำด้วยเวลา UTC จริง (offset สูงสุด ±14 ชม.)

**2. clamp วันสิ้นเดือนด้วย RFC 5545 ล้วน**

`BYMONTHDAY=31` → `BYMONTHDAY=28,29,30,31;BYSETPOS=-1` = "วันสุดท้ายในชุดนี้ที่มีจริงในเดือนนั้น" = `min(31, วันสุดท้ายของเดือน)`

- ใช้กับ MONTHLY และ YEARLY ที่มีเดือนเดียว (29 ก.พ. → 28 ก.พ. ในปีปกติ) และกับกฎที่ไม่ระบุวัน (ใช้วันของ `startsAt`)
- ไม่แตะกฎที่มี `BYDAY` หรือ `BYSETPOS` อยู่แล้ว และกฎที่มีหลายวันต่อเดือน — `BYSETPOS` ทำงานต่อช่วงของ FREQ จึงใช้ได้เฉพาะเมื่อแต่ละช่วงมีเป้าหมายวันเดียว
- แปลงตอนคำนวณเท่านั้น — สิ่งที่เก็บใน DB และแสดงผู้ใช้ยังเป็น `BYMONTHDAY=31` ตามที่ผู้ใช้เลือก

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                              | เหตุผลที่ไม่เลือก                                                              |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| `tzid` ของ rrule.js                                   | ผลข้าม DST ขึ้นกับ runtime · ทดสอบให้มั่นใจบน Node + เบราว์เซอร์ทุกตัวไม่ได้   |
| คำนวณเป็น UTC ตรง ๆ                                   | 09:00 กรุงเทพ ถูก แต่ 09:00 New York เลื่อนไป 1 ชม. ครึ่งปี                    |
| ปล่อยตาม RFC (ข้ามเดือน)                              | บิลหายเงียบ ๆ — แย่กว่าการเลื่อนวันที่ผู้ใช้มองเห็น                            |
| ให้ผู้ใช้เลือก "วันสุดท้ายของเดือน" (`BYMONTHDAY=-1`) | ถูกต้องเฉพาะวันที่ 31 · ผู้ใช้ที่เลือก 30 ยังหาย ก.พ. · และต้องรู้ว่าต้องเลือก |
| post-process หลัง rrule (เติมวันที่หายเอง)            | ต้องเขียนตรรกะปฏิทินเองซ้ำกับ rrule และ COUNT จะนับผิด                         |

## ผลที่ตามมา

**ได้:**

- ผลเหมือนกันทุก runtime — preview (API), materialize (cron) และ mock ใน e2e ใช้ engine ตัวเดียวกัน
- COUNT นับรอบที่ถูก clamp เป็นรอบปกติ — "จ่าย 12 งวด" ได้ 12 งวดจริง
- DoD: บิลวันที่ 31 → 31 ม.ค., 28 ก.พ., 31 มี.ค. ทดสอบทั้งใน integration, builder test ฝั่ง web และ Playwright

**เสีย:**

- "ทุกวันที่ 31" ไม่ใช่ความหมายตาม RFC 5545 แล้ว — ถ้าส่งออก iCal ในอนาคตต้องส่งสตริงที่แปลงแล้ว ไม่ใช่สตริงที่เก็บ
- กฎหลายวันต่อเดือน (`BYMONTHDAY=15,31`) ยังข้ามเดือนสั้นตาม RFC — ยอมรับเพราะ UI ยังสร้างกฎแบบนี้ไม่ได้
- ต้องดูแล `toFloating` / `fromFloating` เอง (ราว 30 บรรทัด) แทนการพึ่งไลบรารี
- ทุกการเรียกสร้าง `RRule` ใหม่ (ไม่ cache) — ยอมรับได้เพราะ cron ทำครั้งละไม่เกิน 200 rule
