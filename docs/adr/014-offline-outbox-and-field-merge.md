# ADR-014: Offline = outbox ใน IndexedDB + `/sync/push` ที่ idempotent ด้วย opId · conflict ระดับ field จาก "ค่าก่อนแก้"

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-16

## บริบท

Phase 7 (สเปก 7.4, 8.6) ต้องการ: ใช้แอปได้ตอนไม่มีเน็ต แล้วข้อมูลขึ้น server ครบเมื่อเน็ตกลับมา — **ไม่ซ้ำ** และ **ไม่ทับงานจากอุปกรณ์อื่นเงียบ ๆ**
ข้อจำกัดที่มีอยู่แล้ว: access token อยู่ใน memory ของหน้าเท่านั้น (ADR/บท 04) · entry มี `version` (optimistic concurrency) แต่ไม่มีประวัติรายช่อง ·
web ใช้ TanStack Query (แคชในหน่วยความจำ) · ห้ามเพิ่ม dependency ที่อายุไม่ถึง 3 วัน

## การตัดสินใจ

**1. Outbox ฝั่ง client (IndexedDB) + ทางแยกเดียวที่ชั้น api**

- ทุก mutation ของรายการผ่าน `runOrQueue`: ออฟไลน์ / คิวมีของ / เน็ตหลุดกลางทาง → เข้าคิว · ออนไลน์ → API ตรง · server ตอบ error → โยนต่อ
- คิวส่งตามลำดับ ≤ 100 ต่อคำขอ · ลบเมื่อ server ตอบผลแล้วเท่านั้น · คิวแยกตามผู้ใช้
- TanStack Query: mutation `networkMode: 'always'` (ให้ทางแยกของเราตัดสิน)

**2. `POST /sync/push` — idempotent ระดับ operation ด้วย `opId` + ตาราง `sync_ops (userId, opId) unique`** เก็บผล 30 วัน ·
ทุก operation เรียก service ตัวเดิมของ endpoint ปกติ · ผลรายตัว (partial success)

**3. Conflict ระดับ field จาก `base` (ค่าก่อนแก้ที่ client ส่งมา)** — server = client → ไม่ชน · server = base → client ชนะ · อื่น ๆ → server ชนะ + diff ·
payload เทียบทีละ key · ลบชนะ · complete idempotent

**4. ข้อมูลออฟไลน์ = แคชของ TanStack Query ที่ dehydrate ลง IndexedDB** · SW แคชเฉพาะหน้า (network-first) และ static (cache-first) ไม่แตะ API ·
ตัวตนตอนออฟไลน์ = โปรไฟล์ในแคช (ไม่มี token จนกว่าจะออนไลน์)

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                           | เหตุผลที่ไม่เลือก                                                                                          |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| CRDT / local-first DB (Automerge, RxDB, PowerSync) | เปลี่ยนแหล่งความจริงจาก Postgres ทั้งระบบ · dependency ใหญ่ · เกินความต้องการ (ข้อมูลส่วนตัว ชนกันไม่บ่อย) |
| Last-write-wins ทั้งรายการด้วย `at` ของ client     | ทับงานอีกเครื่องเงียบ ๆ ทั้งก้อน · นาฬิกามือถือเชื่อไม่ได้                                                 |
| ใช้ `version` อย่างเดียว (409 = ชน)                | บอกได้แค่ "มีคนแก้" ไม่รู้ว่าช่องไหน → ทุกการแก้คนละช่องกลายเป็น conflict                                  |
| เก็บประวัติรายช่องบน server (event log ต่อ field)  | ตาราง/การเขียนเพิ่มทุก PATCH เพื่อแก้ปัญหาที่ client ส่ง base มาก็แก้ได้                                   |
| Idempotency-Key ทั้งคำขอ                           | ผลเป็นรายตัว และชุดที่ส่งซ้ำอาจไม่เหมือนชุดเดิม — key ต้องอยู่ระดับ operation                              |
| SW แคช response ของ API (stale-while-revalidate)   | SW ไม่มี token · แคช HTTP ไม่รู้ว่าข้อมูลไหนใหม่กว่า · invalidate ยาก                                      |
| Workbox / `@tanstack/query-persist-client`         | ใช้แค่เศษเสี้ยว — ราว 150 บรรทัดเขียนเองอ่านเข้าใจทั้งหมด ไม่มี dependency เพิ่ม                           |

## ผลที่ตามมา

**ได้:**

- DoD ผ่านกับ API + Postgres จริง (Playwright smoke): ตัดเน็ต → รีเฟรช → สร้าง 3 งาน → ต่อเน็ต → server มีครบ 3 ไม่ซ้ำ
- ส่งซ้ำได้ทุกเมื่อ (เลื่อนวัน/สร้างกฎไม่ซ้ำ) · แก้คนละช่องจากสองเครื่องรวมกันอัตโนมัติ · ชนกันแล้วผู้ใช้เห็น diff
- โค้ดผู้เรียกเดิม (toast, ⌘Z, optimistic update) ไม่ต้องรู้ว่าออฟไลน์

**เสีย:**

- operation ที่ไม่อยู่ในคิว (+1 ของนิสัย, bulk, จับเวลา) ยังต้องออนไลน์
- `parse` ตอนออฟไลน์ตีความวันที่ด้วยเวลาตอนซิงก์ ไม่ใช่ตอนพิมพ์
- เขียนรายการกับบันทึก `sync_ops` ไม่อยู่ใน transaction เดียว — server ตายตรงกลางแล้วส่งซ้ำ = ทำซ้ำได้ (หน้าต่างแคบ)
- IndexedDB อาจค้างเงียบ → ทุกการเปิดมีเวลาจำกัดและทางสำรอง (หน่วยความจำ / ไม่มีแคช) ซึ่งแปลว่าบางเครื่องอาจไม่ได้ออฟไลน์เต็มรูปแบบ
