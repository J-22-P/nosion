# ADR-012: NL Parser แบบ rule-based "mask-and-scan" ชุดเดียวทั้ง FE/BE — parser แยกชิ้น โมดูลตีความ

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-16

## บริบท

Phase 5 ต้องให้ "ค่าเน็ต 799 ทุกวันที่ 5" ใน ⌘K กลายเป็นบิลรายเดือนพร้อมการเตือนในคำสั่งเดียว (สเปก 6.4, 8.3) ข้อความมาได้ทั้งไทยและอังกฤษ
ปนกัน และภาษาไทยไม่เว้นวรรคระหว่างคำ ("ส่งรายงานพรุ่งนี้")

ก่อน Phase 5 แต่ละโมดูลเขียน regex ของตัวเองใน `parseNaturalLanguage(input: string)`:
งานจับ "พรุ่งนี้" แบบบวก 24 ชั่วโมงจากเวลา server ส่วนรายจ่ายจับจำนวนเงินกับ "ทุกวันที่ N" ซ้ำอีกชุด สองโมดูลจึงเข้าใจวันที่ไม่ตรงกัน
และหน้าเว็บก็มี regex ชุดที่สามสำหรับ chip ของบันทึกด่วน

## การตัดสินใจ

**parser กลางตัวเดียว (`@nosion/core/nl`) แยกข้อความเป็นชิ้น แล้วให้แต่ละโมดูลตีความผลเอง**

```
ข้อความ ──► parseNaturalText (core/nl — ไม่รู้จักโมดูล)
              │  วันที่ · เวลา · RRULE · priority · #tag · +project · เงิน · ระยะเวลา · ปริมาณ  (+ ตำแหน่ง start/end)
              ▼
   ParserService: module.parseNaturalLanguage(NlResult, ctx) ทุกโมดูลที่เปิด → เรียงตามความมั่นใจ
              ▼
   POST /parse (preview)  ·  POST /parse/commit (server parse ข้อความเดิมใหม่ → entry หรือกฎ + การเตือน)
```

- **mask-and-scan** — matcher รันตามลำดับคงที่ (การเกิดซ้ำ → วันที่ → เวลา → สัญลักษณ์ → ตัวเลข) ส่วนที่ match ถูกทับด้วยช่องว่าง
  ยาวเท่าเดิม ตัวหลังจึงไม่หยิบซ้ำ ("ทุกวันที่ 5" ไม่กลายเป็นเงิน 5 บาท) และ `start/end` ชี้กลับข้อความเดิมได้ตรงสำหรับ highlight / แก้ chip
- **rule-based ไม่ใช้ LLM** — ตอบใน < 1 ms, ทำงาน offline ในเบราว์เซอร์, ผลเหมือนเดิมทุกครั้ง (table-driven test 80 เคสได้)
- **ใช้ร่วม FE/BE** — subpath ที่ไม่แตะ Node และไม่ import rrule · เบราว์เซอร์ highlight ทันที server ตัดสินจริงด้วยโค้ดชุดเดียวกัน
- **ข้อความคือแหล่งความจริงเดียว** — commit ส่งข้อความไม่ส่ง payload · แก้ chip = เขียนข้อความส่วนนั้นใหม่ ·
  สิ่งที่ไม่ได้มาจากข้อความ (หมวดที่เดา) ส่งเป็น `payloadPatch` แล้วตรวจด้วย schema ของโมดูล
- เปลี่ยน signature จากสเปก 6.4: `parseNaturalLanguage(input: string, …)` → `parseNaturalLanguage(text: NlResult, …)`

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                      | เหตุผลที่ไม่เลือก                                                                                           |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| LLM (Claude / GPT) แปลงข้อความ                | ช้า (หลายร้อย ms) และมีค่าใช้จ่ายต่อการพิมพ์ทุก 250ms · ผลไม่คงที่ ทดสอบแบบ table ไม่ได้ · ไม่ทำงาน offline |
| library เช่น chrono-node                      | ไม่รองรับไทย ("บ่าย 2", "2 ทุ่ม", พ.ศ.) · ไม่มี RRULE / เงิน / แท็ก · ต้องเขียนส่วนไทยเองอยู่ดี             |
| regex ต่อโมดูล (แบบเดิม)                      | "พรุ่งนี้" ไม่ตรงกันระหว่างโมดูล · เขียนวันที่ซ้ำทุกโมดูลใหม่ (Phase 6 จะเพิ่มอีก 2)                        |
| parse ฝั่ง server อย่างเดียว                  | chip / highlight ต้องรอ network ทุกตัวอักษร                                                                 |
| ให้ client ส่ง payload ที่ parse แล้วมาบันทึก | client แต่งข้อมูลข้ามการตรวจได้ และ preview กับของที่บันทึกอาจมาจากโค้ดคนละรุ่น                             |

## ผลที่ตามมา

**ได้:**

- วันที่/เวลา/การเกิดซ้ำตรงกันทุกโมดูลและทุกหน้า (⌘K, บันทึกด่วน Tasks/Expenses) — ตามโซนเวลาของผู้ใช้เสมอ
- โมดูลใหม่ (Phase 6) เขียนแค่การตีความ เช่น "วิ่ง 5km 30 นาที" ได้ปริมาณกับระยะเวลามาแล้ว
- ทดสอบได้ละเอียดโดยไม่ต้องมี DB: ทุกเคสเทียบ **ทุกฟิลด์** จึงจับการกินคำเกินได้

**เสีย:**

- คำที่ไม่อยู่ในกฎ = ไม่เข้าใจ ("อีกสามวัน", "สัปดาห์ที่แล้ว", เลขไทยเป็นคำ "สองทุ่ม") — ต้องเพิ่ม matcher เอง
- ความกำกวมถูกตัดสินด้วยกติกาตายตัว: "5 โมง" = 17:00, "อาทิตย์หน้า" = สัปดาห์หน้า, วันในสัปดาห์นับวันนี้ด้วย — อาจไม่ตรงใจทุกคน
- ลำดับ matcher มีผลกับผล — เพิ่ม matcher ใหม่ต้องรันเทสต์ทั้งตารางเสมอ
- ภาษาอื่นนอกจากไทย/อังกฤษไม่รองรับ
