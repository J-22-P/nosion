# ADR-013: นิสัย = กฎการเกิดซ้ำ + entry ต่อรอบ · นับจำนวนด้วย UPDATE ที่ให้ Postgres คำนวณ

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-16

## บริบท

Phase 6 เพิ่ม HabitModule (สเปก 5.4) โดยมีเป้าหมายจริงคือ **พิสูจน์ว่าเพิ่มโมดูลได้โดยแก้ `core/` 0 บรรทัด**
นิสัยต่างจากงานและรายจ่ายตรงที่ "เกิดซ้ำทุกวันโดยธรรมชาติ" และต้องรู้ประวัติรายวันเพื่อนับ streak
และนิสัยแบบนับจำนวน ("ดื่มน้ำ 8 แก้ว") ถูกกด +1 รัว ๆ จากหลายที่ (หน้า `/habits`, การ์ด Today, มือถือ) พร้อมกันได้

## การตัดสินใจ

**1. นิสัยหนึ่งตัว = `RecurrenceRule` (template `module: habit`) · หนึ่งรอบ (วัน) = `Entry` ที่ถือ `currentValue` ของวันนั้น**

- ได้ของจาก Phase 3–5 ทั้งหมดโดยไม่เขียนเพิ่ม: materialize ล่วงหน้า, หยุด/ลบ, การเตือน, ปฏิทินรวม, iCal, ⌘K, parser
- streak คำนวณจากประวัติรอบ (entry) — นับบน "รอบ" ไม่ใช่ทุกวันในปฏิทิน: นิสัยเฉพาะวันจันทร์ไม่ขาดเพราะวันอังคาร
- ทำครบ = `status: done` **หรือ** `currentValue ≥ targetValue` — ปุ่ม complete ตัวกลาง (ปฏิทิน) ใช้ได้โดยไม่ต้องรู้จักนิสัย

**2. +1 / −1 / ติ๊ก = UPDATE คำสั่งเดียวที่คำนวณค่าใหม่ใน SQL**

```sql
UPDATE entries SET
  payload = jsonb_set(payload, '{currentValue}', to_jsonb(GREATEST(0, (payload->>'currentValue')::numeric + $delta))),
  status  = CASE WHEN <ค่าใหม่> >= (payload->>'targetValue')::numeric THEN 'done' ELSE 'pending' END,
  version = version + 1
WHERE id = $id AND "userId" = $user AND module = 'habit' AND "deletedAt" IS NULL
```

ใต้ READ COMMITTED คำสั่งที่สองรอ row lock แล้วประเมินนิพจน์ใน `SET` ใหม่กับแถวเวอร์ชันล่าสุด → +1 พร้อมกัน 8 ครั้ง = 8 เสมอ

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                                | เหตุผลที่ไม่เลือก                                                                                        |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| ตาราง `habits` + `habit_logs` แยก                       | ต้องสอน Today, ปฏิทิน, ⌘K, การเตือนให้รู้จักตารางใหม่ — แก้ core ทันที · ผิดเป้าหมายของ Phase            |
| entry เดียวต่อนิสัย เก็บประวัติเป็น array ใน payload    | ปฏิทิน/Review เห็นแค่วันเดียว · payload โตไม่จำกัด · แก้ประวัติวันเก่าชนกับวันนี้                        |
| อ่าน → คำนวณใน Node → เขียนด้วยเงื่อนไข version + retry | ลองแล้ว (รุ่นแรก): retry 3 รอบไม่พอเมื่อกด +1 พร้อมกัน 8 ครั้ง ค่าหาย · retry ไม่จำกัด = เสี่ยง livelock |
| `SELECT … FOR UPDATE` ใน transaction แล้วค่อย UPDATE    | ถูกต้อง แต่สองรอบ round-trip ถือ lock นานกว่า · UPDATE คำสั่งเดียวได้ผลเดียวกัน                          |

## ผลที่ตามมา

**ได้:**

- HabitModule 662 บรรทัด + `AppModule` 2 บรรทัด · `core/` 0 บรรทัด — Today, ปฏิทิน, Review, ⌘K รองรับเอง
- นับจำนวนไม่หายภายใต้การกดพร้อมกัน (integration test ยิง 8 คำขอพร้อมกัน)

**เสีย:**

- การเขียนค่าของนิสัยเป็น raw SQL — ชื่อคอลัมน์/enum ผูกกับ schema ตรง ๆ (Prisma ไม่ตรวจ) · มี integration test คุม
- นิสัยรายวันสร้าง entry วันละแถวต่อนิสัย (4 นิสัย × 365 วัน ≈ 1,460 แถว/ปี/ผู้ใช้) — ถูกสำหรับ Postgres แต่ไม่ใช่ศูนย์
- "N ครั้งต่อสัปดาห์" ยังใช้รอบรายวัน (ทุกวันมีรอบให้ติ๊ก) แล้วนับรวมเป็นสัปดาห์ — ปฏิทินจึงเห็นรอบทุกวัน
- streak คำนวณสดทุกครั้งจากประวัติ 400 วัน — ยังไม่ cache
