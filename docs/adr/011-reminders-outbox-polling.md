# ADR-011: การเตือนใช้ PostgreSQL เป็น source of truth + sweeper ทุกนาที (outbox + polling publisher)

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-10-15

## บริบท

Reminder Engine (สเปก 6.2) ต้องยิงการแจ้งเตือน "ตรงเวลา ไม่ซ้ำ ไม่หาย" — DoD ของ Phase 4 คือ push ถึงมือถือภายใน ±60 วินาที
การเตือนตั้งล่วงหน้าได้นานหลายเดือน (บิลรายปี) และถูกย้ายเวลาได้ตลอด (เลื่อนวัน, แก้ทั้ง series, ช่วงห้ามรบกวน)

ทางที่ง่ายที่สุดคือ enqueue job เข้า BullMQ พร้อม `delay` ตอนสร้างการเตือน แต่:

1. **Redis ไม่ใช่ที่เก็บข้อมูลถาวร** — restart โดยไม่มี persistence, `FLUSHALL`, หรือย้ายเครื่อง = การเตือนหายเงียบ ๆ ไม่มีใครรู้
2. **ต้อง sync สองที่ทุกครั้งที่เวลาเปลี่ยน** — ย้ายวัน → หา job เก่าไปลบ → enqueue ใหม่ · พลาดจุดเดียว = ยิงผิดเวลา หรือยิงทั้งเก่าและใหม่
3. **API บน Vercel ต้องต่อ Redis ทุก request ที่แก้รายการ** — โควตาฟรีของ Upstash ไม่พอ และ API พังเมื่อ Redis ล่ม

## การตัดสินใจ

**PostgreSQL เก็บ "ต้องเตือนเมื่อไร" (`reminders.fireAt`) · Redis ถือแค่ job ที่จะถึงใน 5 นาทีข้างหน้า**

```
API (Vercel) ── เขียน fireAt ─► PostgreSQL ◄── sweeper ทุก 1 นาที (worker)
                                                    │ fireAt ≤ now + 5 นาที → BullMQ (delay) → processor → push / email
```

- **sweeper** (`apps/worker/src/reminders/sweeper.ts`) — ทุกนาที: ปิดที่พลาดเกิน 1 ชม. → ส่งที่จะถึงใน 5 นาทีเข้าคิวพร้อม delay
- **jobId = `reminderId-fireAtMs`** — BullMQ ไม่รับ id ซ้ำ: sweep ซ้ำทุกนาทีหรือรันซ้อนกันได้ · Redis ถูกล้าง = รอบถัดไปส่งเข้าคิวใหม่เอง
  (ไม่กรอง `jobId IS NULL` — ถ้ากรอง การเตือนที่ job หายไปกับ Redis จะไม่ถูกส่งอีกเลย)
- **processor** ตรวจสถานะล่าสุดจาก DB ก่อนยิงทุกครั้ง: ไม่ใช่ scheduled / `fireAt` ใน job ไม่ตรง DB (job เก่า) / ลบ / ทำเสร็จ / ไม่มีวัน → ไม่ส่ง
- **API แตะแค่ `fireAt`** — ย้ายวันคือ UPDATE แถวเดียวใน transaction เดียวกับการแก้รายการ ไม่ต้องรู้จักคิว
- **ส่งแบบ at-least-once** — retry หลังส่งสำเร็จแต่บันทึกผลไม่ทัน อาจส่งซ้ำ แต่ notification ใช้ `tag` เดียวกันต่อรายการ เครื่องแสดงทับเป็นอันเดียว
- Redis ของ worker แยกจาก Upstash ของ API (worker บน Fly.io) — API ไม่ต้องต่อ Redis เพื่อเรื่องการเตือนเลย

## ทางเลือกที่ไม่เลือก

| ทางเลือก                                        | เหตุผลที่ไม่เลือก                                                                       |
| ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| enqueue พร้อม delay ตอนสร้าง (Redis ถือทั้งหมด) | หายเมื่อ Redis หาย · ต้อง sync สองที่ทุกการย้ายเวลา · API ผูกกับ Redis                  |
| cron ยิงตรงจาก DB ทุกนาที (ไม่มีคิว)            | ไม่มี retry/backoff/DLQ · ยิงตรงนาทีเท่านั้น (ช้าได้ถึง 59 วินาที ชน DoD ±60)           |
| pg-boss / Postgres เป็นคิว                      | ตัดชั้น Redis ได้จริง แต่ถือ connection ค้างกับ Supabase pooler · ทีมรู้จัก BullMQ แล้ว |
| at-most-once (จองสถานะก่อนส่ง)                  | worker ตายกลางการส่ง = การเตือนหายเงียบ — แย่กว่าเห็นซ้ำแล้วถูกทับด้วย tag              |

## ผลที่ตามมา

**ได้:**

- Redis หายทั้งก้อนไม่เสียอะไร — รอบ sweep ถัดไปสร้าง job ใหม่จาก DB
- ทดสอบได้ด้วย DB + Redis จริง: ตรงเวลา (lag < 1 วินาที), sweep พร้อมกันส่งครั้งเดียว, retry, DLQ (`apps/worker/test/reminders.int-spec.ts`)
- ทุกการย้ายเวลา (เลื่อนวัน, แก้ series, ช่วงห้ามรบกวน) เป็นการแก้ `fireAt` อย่างเดียว

**เสีย:**

- query ทุกนาทีแม้ไม่มีอะไรต้องเตือน (มี index `(status, fireAt)` — ถูกมาก แต่ไม่ใช่ศูนย์)
- การเตือนที่ตั้ง "ภายใน 1 นาทีข้างหน้า" อาจช้าได้ถึงรอบ sweep ถัดไป (≤ 60 วินาที)
- พลาดเกิน 1 ชม. (worker ล่มนาน) ถูกปิดเป็น failed ไม่ส่งย้อนหลัง — ตั้งใจ แต่เป็นการเตือนที่ "หาย" ในมุมผู้ใช้
- ซ้ำได้ในกรณีหายาก — ช่องทาง email ไม่มี `tag` ให้ทับ จึงอาจเห็นสองฉบับ
